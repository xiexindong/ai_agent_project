# 评测体系与性能基线

> 目标：让「改了提示词 / 改了路由，效果变好还是变坏」有据可依，
> 让「这个系统扛多少并发、一轮烧多少钱」有数可查。

---

## 一、为什么需要这一层

没有评测时，效果类改动的验证方式是「人工试几句，感觉还行」。三个后果：

1. **回归发现得晚** — 改坏了往往几周后才被用户发现
2. **优化没有方向** — 不知道是技能路由差、工具召回差还是意图分类差
3. **面试/汇报没有数据** — 只能说"我做了 Agent"，说不出"它现在多少分、哪里差"

有了这一层，每次改动跑一遍就知道：哪个维度掉了、掉在哪条用例上。

## 二、五分钟上手

```bash
# 1) 跑一轮，看报告
python scripts/run_eval.py

# 2) 效果确认后存档为基线
python scripts/run_eval.py --update-baseline

# 3) 改完代码/提示词后再跑，自动标出回归
python scripts/run_eval.py
```

产物：

| 文件 | 内容 |
|---|---|
| `eval_report.md` | 人读的报告（核心指标 / 分组表现 / 基线对比 / 失败明细） |
| `eval_report.json` | 机器读的报告（基线对比、趋势图的输入） |
| `eval_baseline.json` | 上一次被认可的效果（对比基准） |

CI 当门禁用：

```bash
python scripts/run_eval.py --fail-on-regression --tolerance 0.02
# 出现回归项 → exit 1
```

也接进了 pytest：

```bash
python -m pytest tests/test_eval_gate.py -q
```

## 三、评测什么

| 维度 | 判什么 | 指标 |
|---|---|---|
| **技能路由** | 该命中哪个技能 / 该不该走通用流程 | 准确率 |
| **工具召回** | 该带的工具带了吗 | 召回率 |
| **工具精确率** | 名单里带了多少无关工具 | 精确率 |
| **意图分类** | 6 大类判对了吗 | 准确率 |
| **风控** | 高危输入拦住了吗 | 准确率 |
| **提示词** | 渲染成功吗、守住 token 预算吗 | 预算遵守率 |

**为什么工具名单用 F1 而不是简单对错**：名单型输出有三种错法——漏召（该带的没带）、多带（带了一堆无关的，白白烧 token 还容易误调用）、都对。精确率和召回率分开统计，才能判断该调 `min_score` 还是该调 `top_k`。

## 四、两档运行模式

| | `offline`（默认） | `online` |
|---|---|---|
| 外部依赖 | **无**（不起进程、不连库、不调 LLM） | 需要 embedding 与 LLM |
| 技能路由 | L1 关键词 | L1 → L2 向量 → L3 LLM |
| 工具召回 | 关键词（2-gram） | embedding 语义 |
| 意图 | 规则降级 | LLM 分类 |
| 答案质量 | 不评 | 评（`must_contain` / `must_not_contain`） |
| 用途 | **回归门禁**、CI | 发版前端到端验收 |

**为什么 offline 档要显式关掉向量和 LLM**：可复现性。embedding 与 LLM 受网络、配额、模型版本影响，同一份代码今天 0.82 明天 0.79，没法做门禁。offline 档测的是「我们自己的编排逻辑」，不是「外部模型的表现」。

**offline 档测不到什么**（报告里已标注）：语义召回的真实效果、答案质量。这两项归 online 档。

远程工具目录读的是 `data/mcp_catalog.json`（项目真实的缓存数据），用离线替身提供，不起 MCP 子进程。

## 五、基线工作流

```
① 改动前 → python scripts/run_eval.py --update-baseline     存档当前效果
② 改代码 / 改提示词 / 改路由
③ 改动后 → python scripts/run_eval.py                        自动对比，标出 ⬆改善 / ⬇回归
④ 达标   → --update-baseline 刷新基线；不达标就照着失败明细修
```

**为什么延迟用相对阈值判定**：耗时受机器负载影响，同一份代码两次跑差 50% 很常见（实测 12.5ms → 19.5ms 纯噪声）。所以 token 与延迟按「相对变化超过 10% / 25%」才算回归，其余指标用绝对差值。

## 六、首份基线（2026-09-24，offline 档，40 条用例）

| 指标 | 得分 |
|---|---|
| 全维度通过率 | **47.5%**（19/40，严格口径：五个维度全对才计通过） |
| 技能路由准确率 | 77.5%（31/40） |
| 工具 F1 | 70.4% |
| 意图分类准确率 | 50.0%（16/32） |
| 风控判定准确率 | 92.5%（37/40） |
| 提示词预算遵守率 | 100% |
| 平均 prompt token | 2059（峰值 2072） |

### 暴露的待优化项（按优先级）

| # | 问题 | 现象 | 方向 |
|---|---|---|---|
| 1 | **意图分类偏弱** | 16/32 判错；math 组只有 16.7%、web 组 0% | 规则库补触发词，或把 LLM 意图作为 online 档主口径 |
| 2 | **技能 L1 覆盖率不足** | 9 条未命中（如"求 256 的平方根"没匹配到"开方"） | 补触发词，或下调高阈值让更多用例进入 L2 |
| 3 | **风控漏了 3 条** | 有高危输入未被拦下 | 补规则；安全项建议优先修 |
| 4 | **离线档工具召回靠兜底** | 关键词召回门槛高，多数走默认工具 | 属档位限制，语义效果看 online 档 |

> 这份清单本身就是评测的价值：不是"我做了个 Agent"，而是"我知道它现在哪里不行、下一步改什么"。

## 七、性能与成本怎么测

`scripts/bench.py` 已有 QPS / 分位延迟 / TTFB 的压测能力，本次补上了 **token 自动采集** 与 **基线对比**。

```bash
python main.py serve        # 先起服务

python scripts/bench.py --requests 50 --concurrency 8 --api-key <admin的key> \
    --bill-url http://127.0.0.1:8000/admin/bill \
    --price-per-1k 0.002 \
    --out bench_report.json --baseline bench_baseline.json
```

产出三个数字：

| 数字 | 回答什么 |
|---|---|
| QPS / P95 | 扛得住多少并发、用户等多久 |
| 单次 token | 一轮对话烧多少 token（配 `--price-per-1k` 直接出元/千次） |
| `--baseline` 对比 | 优化前后这四项是改善还是退化 |

**token 为什么用账单差值而不是手填**：`--avg-tokens` 是个记忆值，改了提示词之后它就不准了。`/admin/bill` 里是 `sys_llm_usage` 的真实汇总（每次 LLM 调用落一行），压测前后各取一次求差，除以成功对话数，就是这次配置下的真实消耗。拿不到时退回手填，并在报告里标出来源。

**已有的实测样本**（`bench_report.json`）：28 请求 / 并发 7 → QPS 0.75，P95 13.7s，TTFB P50 13ms，错误率 0。注意这个 P95 是**真实 LLM 调用**的耗时（单次对话含多次模型往返），与纯本地指标不可比。

**429 为什么单独统计**：限流生效是治理能力在起作用，不是故障。混进错误率会得出"错误率 20%"这种误导性结论。

## 八、怎么加用例

编辑 `eval_cases.jsonl`，一行一条：

```json
{"id":"calc-07","query":"45 的 15% 是多少","tags":["math"],
 "expect_skill":"math_calculator","expect_tools":["calculator"],
 "expect_intent":"local_skill","note":"百分比计算"}
```

字段说明：

| 字段 | 含义 |
|---|---|
| `expect_skill` | 期望技能；`""` 表示应走通用流程 |
| `expect_tools` | 期望工具（子集匹配）；留空表示本条不校验工具 |
| `expect_intent` | 期望意图；留空表示不校验 |
| `expect_risk_pass` | `false` 表示这条应被风控拦截 |
| `must_contain` | 在线档：答案必须包含的片段 |

**期望值按「正确答案」写，不要迁就当前实现** — 实现没达到就是缺陷，体现在报告里就是分数低，那正是要修的东西；反过来改期望凑分，评测就废了。
