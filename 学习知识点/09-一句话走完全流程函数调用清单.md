# 09 一句话走完全流程：逐步函数调用清单

> **本文定位**：把「用户在 CLI 敲一句话 → 拿到回答」经过的**每一个函数**按执行顺序编号列清。
> 与 `全流程执行链路.md` 的区别：那份是**分层架构总览**（一图流），本文是**逐步调用清单**（step by step，可当 debug checklist）。

**样例场景**：

```
$ python main.py chat
[cli-user | a1b2c3d4] > 3*7 等于多少
```

这是一个**走工具调用**的完整场景（最复杂的一种），纯聊天场景见文末对照表。

格式约定：`文件:行号  函数()`，缩进表示调用层级。

---

## 〇、先记住三个数字

| 数字 | 含义 |
|---|---|
| **5** | 图里有 5 个节点：`prepare / reason / act / answer / save` |
| **1** | `invoke` 从入口节点开始，每轮重新走一遍 |
| **0~N** | `act` 节点可能一次都不走（纯聊天），也可能走多次（连续调工具） |

**每轮必定经过 4 个节点**：`prepare → reason → answer → save`。
`act` 看模型决策，走 0~N 次；`reason` 走 1+N 次（每次 act 完都回到它）。

### 阶段 B：引擎点火

| Step | 位置 | 调用 | 作用 |
|---|---|---|---|
| 14 | `graph.py:256` | `run()` | main.py 唯一认识的函数 |
| 15 | `graph.py:266-271` | 构造 `initial_state` | **只有 4 个键**：`session_id / user_id / user_query / prepared=False` |
| 16 | `graph.py:273` | `self._graph.invoke(initial_state, {"recursion_limit": 30})` | **引擎启动**，同步阻塞，直到走完 `END` |

> ⚠ 第 15 步是关键：上轮的 `result` **没有**被传进来。
> 每轮 state 从零开始，**记忆靠 `session_id` 从数据库捞，不靠 state 传递。**

invoke 内部循环（等价逻辑）：

```
node = entry_point  ("prepare")
while node != END:
    updates = 节点表[node](state)   # 执行
    state.update(updates)           # 合并增量
    node = 查边表(node, state)      # 固定边直取 / 条件边调 _should_continue
return state
```

## 四、两种场景的调用次数对比

| 环节 | 纯聊天「你好」 | 调工具「3*7」 |
|---|---|---|
| 遍历节点 | `prepare → reason → answer → save` | `prepare → reason → act → reason → answer → save` |
| `act` 次数 | **0** | 1 |
| `reason` 次数 | 1 | 2 |
| **大模型调用** | **1 次**（reason） | **2 次**（reason ×2） |
| 读 PG | 2 次（长期+短期） | 2 次 |
| 读 Milvus | 1 次（无命中则 0 结果） | 1 次 |
| 写 PG | 2 次（`chat_history` + `chat_session`） | 2 次 |
| embedding | 1 次（问句） | 1~2 次（问句 + 可能的摘要） |

> 注意：`answer` 节点的 `generate_answer` 在**绝大多数情况会短路**（reason 已给答案），
> 只有「模型想调工具但 state.error 非空」等少数情况才会真正调 `llm.invoke`。

## 五、⚠ 读代码时发现的 2 个问题

### Bug 1（严重）：`llm.invoke()` 缺 return，永远返回 `None`

```140:156:modules/agent/llm.py
        try:
            resp = self._client.chat.completions.create(
                model=self._model,
                messages=messages,
                temperature=temperature,
                max_tokens=max_tokens,
            )
            # 响应结构：resp.choices[0].message.content 即第一个候选回答的文本

        except Exception as e:
            _logger.error(f"LLM调用失败: {e}")
            raise LLMException("LLM调用失败", str(e))
```

`resp` 拿到后**没有 `return`**，函数走完隐式返回 `None`。
对比 `invoke_with_tools`（`llm.py:241`）是有 `return {"content":..., "tool_calls":...}` 的。

**受影响的两处**：

| 调用点 | 后果 |
|---|---|
| `react_agent.py:297` `final_answer = self.llm.invoke(prompt)` | 答案变成 `None`，最终打印 `回答: None` |
| `summary_generator.py:48-49` `summary = self._llm.invoke(prompt)` 然后 `.strip()` | 抛 `AttributeError: 'NoneType'`，被 `react_agent.py:322` 捕获 → **摘要永远降级成 `query[:50]`** |

**为什么平时没炸**：
- 答案 < 100 token 时 `summary_generator.py:45` 直接截断返回，不调 LLM
- `generate_answer` 的短路分支（285 行）在多数场景生效

**修复**（加一行）：

```python
            return resp.choices[0].message.content.strip()
```

### Bug 2（设计）：`save` 节点两条写库共用一个 try

```182:222:modules/agent/graph.py
            try:
                ...
                self.agent.memory.save_turn(...)          # 写 chat_history
                ...
                self.agent.memory.pg.update_session_state(...)  # 写 chat_session
            except Exception as e:
                _logger.error(f"记忆保存异常: {e}")
```

`save_turn` 一失败，`update_session_state` 就**根本不执行**。两者无依赖关系，建议拆成两个 try。

### 附带：`breakpoint()` 在 try 之外

`graph.py:178` 的 `breakpoint()` 位于 `try`（182 行）**之前**。
非交互环境（API 服务）下它会抛 `BdbQuit` 并**直接冒泡穿过 invoke**，整条链路挂掉。
临时止血：启动时设 `PYTHONBREAKPOINT=0`。

## 六、一句话总结

> **启动时装满 `ReActAgent` 盒子 → 每轮回车造一个 4 键新 state → `invoke` 从 `prepare` 重新走一遍 5 节点 →
> `prepare` 从库里捞记忆、`reason` 问 LLM、`act` 跑工具、`answer` 收尾、`save` 写回库 →
