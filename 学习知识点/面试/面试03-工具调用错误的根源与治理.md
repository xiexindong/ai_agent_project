# 面试03：Agent 选错工具、填错参数，根源是什么？怎么治？

> 配套代码：`modules/tools/retry.py`（新增实现）、`modules/tools/base_tool.py:127-173`、`modules/harness/middleware.py:62-127`、`modules/agent/react_agent.py:458-468`、`modules/tools/tool_rag.py`
> 一句话结论：**错误的根源分三层——模型层（幻觉）、描述层（工具画像写得差）、入口层（给模型的工具太多太像）；治理是"四道工序"：源头少给（Tool-RAG）→ 参数校验（Schema）→ 执行重试（瞬时故障）→ error 回喂（让模型自己改）。**

---

## 一、先说结论：三层根源 × 四道工序

| 根源层 | 具体表现 | 对应工序 | 代码位置 |
|---|---|---|---|
| 模型层：幻觉 | 编造不存在的工具名 `calc`、不存在的参数名 `expr` | 存在性检查 + Schema 校验 | tool_registry.py:247 / middleware.py:62 |
| 模型层：输出损坏 | tool_calls 的 JSON 带尾逗号、缺括号 | `repair_json` 自动修复 | react_agent.py:458-462 |
| 描述层：画像差 | `description` 写得太泛，两个工具看着都能干 | 人工写清"能干什么、不能干什么" | 各工具类 + tool_rag 画像 |
| 入口层：候选过多 | 上百个工具全量塞给模型，选择难度爆炸 | Tool-RAG 语义召回 top-5 | tool_rag.py:172 |
| 执行层：瞬时故障 | 超时、连接断开——不是模型的错 | 自动重试 2 次、指数退避 | retry.py（新增） |
| 执行层：确定性失败 | 参数缺失、权限不足 | error 中文原因回喂模型 | base_tool.py:43 |

---

## 二、大白话拆解：一次失败调用的完整旅程

```
LLM 生成 tool_calls: calculator(expr="3*7")        ← 参数名写错了（幻觉）
   ↓
SchemaMiddleware.check (middleware.py:123)
   "缺少必填参数 ['expression']"                    ← ① 拦下，不执行
   ↓（假如参数对，进入执行）
ToolConcurrencyGuard → ToolRetryPolicy → tool.run()
   run() 内部 (base_tool.py:151-173):
     validate_params → execute → 异常兜成 ToolResult(success=False, error=...)
   ↓
error 文本回喂给 LLM（下一轮 reason 的 observation）
   ↓
LLM 看到 "缺少必填参数 ['expression']"，改参数重试
```

| 工序 | 大白话解释 |
|---|---|
| SchemaMiddleware | 考官：按工具说明书（JSON Schema）查模型交的卷子，缺项/多项/类型错都打回 |
| repair_json | 卷子本身烂了（JSON 非法）先粘一粘再判，粘不好才判错 |
| ToolRetryPolicy | 判卷后分类：临时抖动（超时）→ 隔 0.5s 重考一次；真不会（参数错）→ 直接把错题告诉模型 |
| error 回喂 | 错题本不是给人看的，是给模型看的：它看到"缺什么"才知道下一轮补什么 |

## 三、输入 → 输出对照（本机实测）

```python
reg = ToolRegistry(); reg.register(CalculatorTool())

# 正常调用
reg.execute_tool("calculator", {"expression": "3*7"}, session_id="s1")
# 运行结果: success=True, result=21

# 参数错误（确定性失败，不重试）
reg.execute_tool("calculator", {}, session_id="s1")
# 运行结果: success=False, error="工具参数缺失: calculator 缺少必填参数 ['expression']"
# 日志: 工具 calculator 失败且非瞬时故障，不重试

# 重试策略（本机实测）
rp = ToolRetryPolicy(max_retries=2, backoff=0.01)
rp.run("t", lambda: ToolResult(success=False, error="Connection timeout"))
# 运行结果: 共执行 3 次（首次 + 重试 2 次），退避 0.5 → 1.0 秒指数递增

rp.run("t", lambda: ToolResult(success=False, error="工具参数缺失: ..."))
# 运行结果: 共执行 1 次 —— 确定性失败不重试

# 瞬时故障判定
is_transient("Connection timeout")   # True
is_transient("MCP Server 不可用")     # True
is_transient("工具参数缺失: ...")     # False
is_transient("当前身份无权调用工具")  # False
```

## 四、为什么要这么写

| 做法 | 原因（不这么写会怎样） |
|---|---|
| 区分瞬时故障与确定性失败 | 无脑重试：参数错也打 3 次下游 + 白等 1.5 秒；一轮 ReAct 5 次调用 = 15 次下游请求 |
| 指数退避（0.5→1.0→2.0） | 固定间隔重试恰好在下游恢复窗口外再撞一次；指数拉开间隔给下游喘息 |
| 校验放执行**之前**（中间件） | 等下发到真实服务再报错，副作用已经发生（通知发出去了、数据删了） |
| error 用中文具体原因 | 模型看到"缺什么参数"才会补；只回 "error" 一个词模型只能瞎猜 |
| 只缓存成功结果 | 失败结果被缓存回传，模型会以为"答案就是这样"，失去改参数的机会 |
| Tool-RAG 源头只给 top-5 | 全量给 100 个工具：prompt 膨胀 + 选项越多选错率越高（详见面试08） |

## 五、失败分类速查表（面试可直接背）

| 失败类型 | 例子 | 处理 | 谁来纠正 |
|---|---|---|---|
| 幻觉工具名 | `calc` 不存在 | 存在性检查拦截 | 模型（看 error 改名） |
| 参数缺失/类型错 | `expr` ≠ `expression` | Schema 校验拦截 | 模型（看 error 改参数） |
| JSON 输出损坏 | 尾逗号、缺括号 | repair_json 修复 | 框架（模型无感） |
| 瞬时执行故障 | 超时、连接断 | 自动重试 2 次 | 框架（模型无感） |
| 权限/越界 | 无 `tool:data_query` 权限 | 中间件拦截 | 模型（换工具）或人工（授权） |
| 死循环 | 同参反复调 | 去重 + 单工具 5 次上限 | 框架强制拦截 |

---

## 六、简单总结

1. 根源三层：**模型幻觉**（改名改参数）、**描述歧义**（画像不清）、**入口过载**（工具太多）；只有第一种是"模型的错"，后两种是工程的错
2. 治理四道工序：Tool-RAG 少给（top-5、阈值 0.25）→ Schema 先拦 → 瞬时故障自动重试（2 次、指数退避 0.5s 起）→ error 中文原因回喂
3. 关键分界线：**瞬时故障框架兜（模型无感），确定性失败回喂模型（模型自纠）**——重试只治超时/连接类，参数错重试一百次结果也一样
