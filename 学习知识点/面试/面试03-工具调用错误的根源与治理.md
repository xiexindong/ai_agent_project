# 面试03：Agent 选错工具、填错参数，根源是什么？怎么治？

> 配套代码：`modules/tools/retry.py`（重试策略）、`modules/tools/base_tool.py:127-173`（校验+统一执行入口）、`modules/harness/middleware.py:62-127`（Schema 校验中间件）、`modules/agent/llm.py:408`（tool_calls 的 repair_json 修复）、`modules/tools/tool_rag.py:172`（Tool-RAG 召回）
> 一句话结论：**错误的根源分三层——模型层（幻觉）、描述层（工具画像写得差）、入口层（给模型的工具太多太像）；治理是"四道工序"：源头少给（Tool-RAG）→ 参数校验（Schema）→ 执行重试（瞬时故障）→ error 回喂（让模型自己改）。**

---

## 〇、面试官视角与 30 秒回答

**面试官到底想问什么**：不是问"LLM 为什么会犯错"（幻觉是公开常识），而是考你能不能把"错误"分层归因，并且每一层都给出对应的工程手段——尤其考你是否知道"哪些错让框架兜、哪些错必须还给模型自己改"这条分界线。

**30 秒回答模板**：

> "我把工具调用错误按根源分三层：模型层是幻觉——编造不存在的工具名或参数名；描述层是工具画像没写清'能干什么不能干什么'，两个工具看着都能干；入口层是把上百个工具全量塞给模型，选择难度爆炸。治理对应四道工序：入口用 Tool-RAG 语义召回只给 top-5，从源头减少选错面；执行前用 Schema 中间件按工具说明书校验参数，缺参/错类型直接拦截，副作用不发生；执行中对瞬时故障——超时、连接断开——按指数退避自动重试 2 次，这类错不是模型的责任；最后把中文错误原因回喂给模型，让模型下一轮自己改参数或换工具。关键分界线是：瞬时故障框架兜底、模型无感；确定性失败回喂模型、模型自纠。"

**术语首次出现的大白话**：

| 术语 | 大白话 |
|---|---|
| 幻觉（hallucination） | 模型"一本正经地瞎编"：明明没有 `calc` 这个工具，它照调不误 |
| Function Calling / tool_calls | 模型不直接执行动作，而是"填一张工单"：写明要调哪个工具、传什么参数，由程序代劳 |
| JSON Schema | 工具的"说明书/考卷评分标准"：每个参数叫什么、什么类型、哪些必填，一条条列清 |
| ReAct | 模型"想一步、做一步、看结果、再想下一步"的循环工作法（Reason + Act） |
| observation | 循环里"看结果"那一步：工具执行的返回值或失败原因，回喂给模型 |
| 指数退避 | 重试间隔越来越长：等 0.5 秒、再等 1 秒、再等 2 秒——给下游喘息时间，别堵在门口反复敲门 |
| 瞬时故障 vs 确定性失败 | 瞬时：快递路上堵车，等会儿再送能到；确定性：地址写错了，再送一百次也到不了 |

## 一、先说结论：三层根源 × 四道工序

| 根源层 | 具体表现 | 对应工序 | 代码位置 |
|---|---|---|---|
| 模型层：幻觉 | 编造不存在的工具名 `calc`、不存在的参数名 `expr` | 存在性检查 + Schema 校验 | tool_registry.py:290 / middleware.py:62 |
| 模型层：输出损坏 | tool_calls 的 JSON 带尾逗号、缺括号 | `repair_json` 自动修复 | modules/agent/llm.py:408（定义在 common/validator.py:156） |
| 描述层：画像差 | `description` 写得太泛，两个工具看着都能干 | 人工写清"能干什么、不能干什么" | 各工具类 + tool_rag 画像 |
| 入口层：候选过多 | 上百个工具全量塞给模型，选择难度爆炸 | Tool-RAG 语义召回 top-5 | tool_rag.py:172 |
| 执行层：瞬时故障 | 超时、连接断开——不是模型的错 | 自动重试 2 次、指数退避 | retry.py:39（ToolRetryPolicy） |
| 执行层：确定性失败 | 参数缺失、权限不足 | error 中文原因回喂模型 | base_tool.py:50（ToolResult.error 字段约定） |

## 二、大白话拆解：一次失败调用的完整旅程

```
LLM 生成 tool_calls: calculator(expr="3*7")        ← 参数名写错了（幻觉）
   ↓
SchemaMiddleware.check (middleware.py:123)
   "缺少必填参数 ['expression']"                    ← ① 拦下，不执行
   ↓（假如参数对，进入执行）
ToolConcurrencyGuard → ToolRetryPolicy → tool.run()
   run() 内部 (base_tool.py:151-173):
     validate_params → execute → 异常兜成 ToolResult(success=False, error=...)
   ↓
error 文本回喂给 LLM（下一轮 reason 的 observation）
   ↓
LLM 看到 "缺少必填参数 ['expression']"，改参数重试
```

| 工序 | 大白话解释 |
|---|---|
| SchemaMiddleware | 考官：按工具说明书（JSON Schema）查模型交的卷子，缺项/多项/类型错都打回 |
| repair_json | 卷子本身烂了（JSON 非法）先粘一粘再判，粘不好才判错 |
| ToolRetryPolicy | 判卷后分类：临时抖动（超时）→ 隔 0.5s 重考一次；真不会（参数错）→ 直接把错题告诉模型 |
| error 回喂 | 错题本不是给人看的，是给模型看的：它看到"缺什么"才知道下一轮补什么 |

Schema 校验的真实代码（middleware.py:79-89，三道检查：缺必填/多未知/错类型）：

```python
missing = [r for r in required if r not in arguments or arguments[r] is None]
if missing:
    return "schema_invalid", f"缺少必填参数 {missing}"

unknown = [k for k in arguments if k not in properties and not str(k).startswith(_PRIVATE_PREFIX)]
if unknown:
    return "schema_invalid", f"出现未知参数 {unknown}（请只使用工具声明的参数）"
```

重试分类的真实代码（retry.py:96-113）：

```python
result = fn()
for attempt in range(1, total + 1):
    if result.success:
        return result
    if not self.is_transient(error):           # 确定性失败：立刻回喂模型
        return result
    if attempt >= total:
        break
    wait = self._backoff * (2 ** (attempt - 1))    # 0.5 → 1.0 → 2.0 指数退避
    time.sleep(wait)
    result = fn()                              # 瞬时故障：退避后再试
```

## 三、输入 → 处理 → 输出对照（本机实测）

```python
reg = ToolRegistry(); reg.register(CalculatorTool())
```

| 场景 | 输入 | 处理 | 输出 |
|---|---|---|---|
| 正常调用 | `execute_tool("calculator", {"expression": "3*7"})` | 校验过 → 真跑计算 | `success=True, result=21` |
| 参数错误 | `execute_tool("calculator", {})` | run() 内 validate_params 抛 ToolException → 兜成失败结果；非瞬时故障 → 不重试 | `success=False, error="工具参数缺失: calculator 缺少必填参数 ['expression']"`；日志"失败且非瞬时故障，不重试" |
| 瞬时故障重试 | `ToolRetryPolicy(max_retries=2, backoff=0.01).run("t", 每次都超时)` | 失败→退避→再试 | 共执行 3 次（首次 + 重试 2 次），正式配置退避 0.5 → 1.0 秒指数递增 |
| 确定性失败不重试 | `rp.run("t", 返回"工具参数缺失: ...")` | is_transient 判 False | 共执行 1 次，立刻返回 |

瞬时故障判定速查：

```python
is_transient("Connection timeout")   # True
is_transient("MCP Server 不可用")     # True
is_transient("工具参数缺失: ...")     # False
is_transient("当前身份无权调用工具")  # False
```

## 四、为什么要这么写

| 做法 | 原因（不这么写会怎样） |
|---|---|
| 区分瞬时故障与确定性失败 | 无脑重试：参数错也打 3 次下游 + 白等 1.5 秒；一轮 ReAct 5 次调用 = 15 次下游请求 |
| 指数退避（0.5→1.0→2.0） | 固定间隔重试恰好在下游恢复窗口外再撞一次；指数拉开间隔给下游喘息 |
| 校验放执行**之前**（中间件） | 等下发到真实服务再报错，副作用已经发生（通知发出去了、数据删了） |
| error 用中文具体原因 | 模型看到"缺什么参数"才会补；只回 "error" 一个词模型只能瞎猜 |
| 只缓存成功结果 | 失败结果被缓存回传，模型会以为"答案就是这样"，失去改参数的机会 |
| Tool-RAG 源头只给 top-5 | 全量给 100 个工具：prompt 膨胀 + 选项越多选错率越高（详见面试08） |

## 五、失败分类速查表（面试可直接背）

| 失败类型 | 例子 | 处理 | 谁来纠正 |
|---|---|---|---|
| 幻觉工具名 | `calc` 不存在 | 存在性检查拦截 | 模型（看 error 改名） |
| 参数缺失/类型错 | `expr` ≠ `expression` | Schema 校验拦截 | 模型（看 error 改参数） |
| JSON 输出损坏 | 尾逗号、缺括号 | repair_json 修复 | 框架（模型无感） |
| 瞬时执行故障 | 超时、连接断 | 自动重试 2 次 | 框架（模型无感） |
| 权限/越界 | 无 `tool:data_query` 权限 | 中间件拦截 | 模型（换工具）或人工（授权） |
| 死循环 | 同参反复调 | 去重 + 单工具 5 次上限 | 框架强制拦截 |

### 关键设计对照表：三种"出错怎么办"策略对比

| | 方案 A：报错直接抛给用户 | 方案 B：框架无脑重试 N 次 | 方案 C：分类治理（本项目） |
|---|---|---|---|
| 瞬时故障（超时） | 用户看到偶发失败，体验差 | 能兜住，但参数错也跟着重试 | 指数退避重试，模型无感 |
| 确定性失败（参数错） | 用户看到一堆栈信息 | 白打 3 次下游 + 白等 1.5s | 立刻把中文原因回喂模型自纠 |
| 模型能不能学到教训 | 不能 | 不能 | 能——error 即 observation |
| 下游压力 | 最小 | 放大 N 倍 | 只对值得的重试放大 |

## 六、面试话术（可直接背）

> "工具调用的错误我按'谁的错'分类治理。模型的错——幻觉工具名、填错参数——治理重点是把错误变成模型能看懂的信息：Schema 中间件在执行前拦截，回一句中文的'缺少必填参数 expression'，模型下一轮自己就改对了；框架的错——瞬时超时、连接断开——不该打扰模型，指数退避自动重试两次兜住。另外两道防线在源头：Tool-RAG 只给 top-5 候选，把选错率压下去；工具的 description 写清边界，把歧义压下去。整条链路的总原则是：能自动修的（JSON 损坏）悄悄修，该重试的（瞬时故障）框架扛，改不了的（确定性失败）说清楚让模型自己想办法——绝不把栈和异常抛给用户。"

## 七、高频追问（含回答要点）

**Q1：怎么区分"该重试"和"不该重试"？**
- 要点：看 error 文本是否命中瞬时故障清单（retry.py:27-33）：timeout/超时/connection/连接/unavailable/不可用/reset/502/503/504；
- 判定原则是**宁可漏判不可误判**：漏判=少试一次，失败照常回喂；误判=对参数错白打两次下游还拖慢整轮；
- 参数缺失、权限不足、工具不存在这类，重试一百次结果一样，直接回喂。

**Q2：error 回喂具体回什么？为什么用中文？**
- 要点：回具体原因而不是笼统的 "error"——如"缺少必填参数 ['expression']"、"当前身份无权调用工具 data_query"；
- 原因：error 会成为下一轮 ReAct 的 observation，模型据此改参数/换工具；信息越具体，纠偏越快；
- 用中文是因为系统提示词与用户上下文是中文，同语言回喂减少模型理解损耗（base_tool.py:50 的字段约定就是这个用途）。

**Q3：repair_json 修不了的情况怎么办？**
- 要点：repair_json 只修小毛病（尾逗号、缺括号、夹带多余文本），修不了返回 None；
- 兜底：react_agent.py:846 附近——修复后仍无有效参数时不硬调工具，改为向用户追问缺失参数；
- 原则：修得好就当没发生过，修不好就如实说，绝不带着半烂的 JSON 去撞下游。

**Q4：为什么校验要放中间件（执行前），而不是让工具自己报错？**
- 要点：有副作用的工具（发通知、删数据）等执行到一半报错，副作用已经发生，无法撤回；
- 中间件拦截时真实服务收不到任何请求，是"零副作用拦截"；
- 工具内的 validate_params（base_tool.py:127-138）是第二道兜底——没装 harness 的中间件链时（如单测），参数校验仍然生效。

**Q5：怎么防模型陷入"调错→改→又错"的死循环？**
- 要点：三道保险：同参去重（相同参数调过就直接回传缓存或拒绝）、单工具 5 次上限（超限拦截并提示换思路）、会话总预算（token/次数/墙钟，打满强制收尾）；
- 设计意图：让模型看到"此路不通"后主动换思路，而不是无限制撞同一堵墙；
- 被拦也回中文原因（"疑似死循环，已拦截"），模型收到后通常会收尾或求助用户。

## 八、简单总结

1. 根源三层：**模型幻觉**（改名改参数）、**描述歧义**（画像不清）、**入口过载**（工具太多）；只有第一种是"模型的错"，后两种是工程的错
2. 治理四道工序：Tool-RAG 少给（top-5、阈值 0.25）→ Schema 先拦 → 瞬时故障自动重试（2 次、指数退避 0.5s 起）→ error 中文原因回喂
3. 关键分界线：**瞬时故障框架兜（模型无感），确定性失败回喂模型（模型自纠）**——重试只治超时/连接类，参数错重试一百次结果也一样
