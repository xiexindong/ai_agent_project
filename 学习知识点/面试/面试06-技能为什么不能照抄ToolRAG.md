# 面试06：工具能 top-5 让模型自己挑，技能为什么必须单选 + 三级路由？

> 配套代码：`modules/skills/skill_registry.py:360-383`（match 主入口）、`modules/tools/tool_rag.py:172`
> 一句话结论：**因为两者注入的东西不一样——工具注入的是"候选清单"（多给几个无害，模型自己挑对的），技能注入的是"整段 SOP 作业流程"（两份混着必打架），误判代价不对称决定了工具要 top-k 排序、技能必须单选三级兜底。**

---

## 一、先说结论

| 面试问 | 一句话答 |
|---|---|
| 技能为什么不能照抄 Tool-RAG？ | 工具多选无害（top-5 候选清单）；技能多选必冲突（两段 SOP 混注互相打架） |
| 为什么单选就得多级？ | 单选 = 必须选"对"那一个，错不起；三级漏斗逐级加码，一层比一层准 |
| 串行还是并行？ | 串行，命中即停——L1 定了 L2/L3 根本不执行 |
| 向量能推翻关键词吗？ | 不能，L2 的候选池就是 L1 的输出（漏斗只收窄不放宽） |

---

## 二、大白话拆解：一张表看懂分岔点

|  | 工具（Tool-RAG） | 技能（SkillRegistry） |
|---|---|---|
| 选几个 | **多个**（top-k，默认 5） | **最多一个**（或没有） |
| 注入什么 | JSON Schema 候选清单 | **整段 SOP 指令文本** |
| 误判代价 | 低：多给几个，模型自己挑 | **高**：选错 SOP 带偏整轮对话 |
| 信号来源 | 自动生成的一句话画像 | **人工写的触发词** + routing_text |
| 数量级 | 可成百上千（远程 MCP） | 人工定义，当前 4 个 |
| 匹配策略 | 单层向量 top-k | **三级串行漏斗** |
| 两份并存 | 无害（模型看到 5 个工具是常态） | **冲突**（"先问清需求再查库" vs "直接查库"，模型精神分裂） |

**最根本的一条**：给模型 5 个工具 = 给它一个菜单；给它 2 段 SOP = 给它两套互相矛盾的命令。菜单多几页没关系，命令只能有一条。

---

## 三、输入 → 输出对照

```python
# 工具侧（tool_rag.py:172 recall）：多选，分数够就都给
recall("今天北京天气怎么样", top_k=5)
# 输出（多选共存，无害）:
# [ToolHit("city_weather", 0.63), ToolHit("web_search", 0.41)]   ← 2 个都进 prompt

# 技能侧（skill_registry.py:360 match）：单选，一次只回一个
match("帮我按报销流程提交发票")
# 输出: SkillMatch(name="expense_reimburse", ...)   ← 只有 1 个
# 即便 L2 向量算出 0.78 和 0.74 两个高分技能，也只返回第 1 个
```

---

## 四、为什么要这么写

| 做法 | 原因（不这么写会怎样） |
|---|---|
| 技能最多激活 1 个 | 两段 SOP 同时注入：模型在"先问需求"和"直接执行"之间反复横跳，输出风格割裂；最坏情况两段的工具调用顺序互相破坏 |
| 工具照旧 top-k | 只给 1 个工具：模型没得选，工具描述稍有偏差就调不了；多给几个 = 给模型留纠错余地 |
| 技能向量不进 Milvus、自己算 | 技能就几个，进 Milvus 是用牛刀杀鸡还多一个外部依赖（详见面试08） |
| 三级漏斗而不是一步到位 | 全靠关键词：换说法就漏；全靠向量：明确提问也要付 embedding 成本；全靠 LLM：每句话多一次调用 |

---

## 五、简单总结

1. 分岔的根：**注入物不同**——工具是候选清单（多选无害），技能是 SOP 指令（多选冲突），误判代价不对称
2. 因此工具走**单层向量 top-k**（tool_rag.py:172），技能走**三级串行漏斗**（skill_registry.py:360），命中即停
3. 记住对比锚点：工具 top-k=**5**、技能单选=**1**；工具阈值 0.25（宽进），技能阈值 0.6/0.75/0.5（层层严判）
