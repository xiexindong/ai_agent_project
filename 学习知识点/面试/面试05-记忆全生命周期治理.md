# 面试05：向量记忆的筛选、冲突、时效、遗忘、隔离，怎么治理？

> 配套代码：`modules/memory/memory_manager.py:53-117`（save_turn 治理流水线）、`modules/memory/memory_manager.py:122`（入库筛选）、`modules/memory/pg_manager.py:830、896`（冲突检测/取代）、`init_db.sql:45-46、80-83`（memory_status 列）、`modules/memory/archiver.py:106`（归档遗忘）
> 一句话结论：**这些问题 90% 不是 embedding 的错，是记忆架构缺"生命周期管理"——本项目补齐了五道工序：入库筛选（挡噪声）→ 用户隔离（user_id 过滤）→ 冲突处理（新取代旧）→ 时效衰减（180 天半衰期）→ 归档遗忘（90 天冷分离 + 物理清除）。**

## 零、先扫盲：本文会用到的术语（大白话版）

| 术语 | 大白话解释 |
|---|---|
| embedding / 向量 | 把一句话翻译成一串数字（本项目 1024 个），语义相近的话数字也相近，像给每句话发一个"语义坐标" |
| 余弦相似度 | 比较两个语义坐标的"方向有多一致"，返回 0~1，越接近 1 越像。就像比较两个人走路的方向，不在乎谁走得远（句子长短），只看朝哪走 |
| 生命周期管理 | 像管冰箱里的食物：进门先检查（筛选）、同类旧的贴"已过期"标签（取代）、放得越久越往后排（衰减）、太老的先拍照留档再扔（归档遗忘） |
| 半衰期 | 借物理名词：每过 180 天，记忆的"排序权重"打对折。180 天前的记忆权重 ×0.5，360 天前 ×0.25 |
| superseded | "已被取代"的状态标签。旧记忆不删，只贴个"此条作废，见新条"的条子 |
| 软删 / 物理删 | 软删 = 贴标签但数据还在（可追溯）；物理删 = DELETE 真删（查无对证） |
| pgvector | PostgreSQL 数据库的向量插件，让普通 SQL 表也能存向量、算相似度 |
| `<=>` | pgvector 的"余弦距离"运算符：0 = 完全一样，2 = 完全相反。相似度 = 1 - 距离 |

## 一、先说结论：五大问题 × 五道工序

| 问题 | 根因 | 工序 | 代码位置 |
|---|---|---|---|
| 无效/玩笑内容入库 | 入库无门槛 | 入库筛选 `_should_memorize` | memory_manager.py:122 |
| 遗忘关键信息 | 长期召回只有相似度 | 时效衰减重排（180 天半衰） | memory_manager.py:311-324 |
| 记忆互相矛盾 | 新旧并存都被召回 | 冲突取代（≥0.90 旧的置 superseded） | pg_manager.py:830、896 |
| 时效性失效 | 只有 created_at 没有状态 | 衰减 + superseded 状态列 | init_db.sql:45-46 |
| 脏记忆难清理 | 只敢软删 | 归档→保留期→物理删 | archiver.py:106 |
| 跨用户泄露 | 召回 SQL 不带 user_id | 所有读写强制 user_id 过滤 | pg_manager.py:780 |

## 二、大白话拆解：一条记忆的一生

```
用户说 "我搬到北京了"
   │
   ▼
① 入库筛选 _should_memorize（memory_manager.py:122）
   长度关(<4字拦) → 寒暄关(整句="你好"拦) → 内容关(纯标点拦)
   "你好" 在这里就死了，根本不落库
   │
   ▼
② 落库 save_history（pg_manager.py:566）
   原文+摘要+双向量+工具日志 一行写入，拿回 id=57
   │
   ▼
③ 冲突检测 find_conflict_memory（pg_manager.py:830）
   用新摘要向量在同用户 active 记忆里找 ≥0.90 的
   → 命中 id=40 "用户住址:上海"（sim=0.93）
   │
   ▼
④ 冲突取代 supersede_memory（pg_manager.py:896）
   UPDATE id=40 SET memory_status='superseded', superseded_by=57
   （不物理删——留审计痕迹）
   │
   ▼
⑤ 未来某天被召回时（search_memory_by_vector，pg_manager.py:713）
   SQL 只取 COALESCE(memory_status,'active')='active'  → 上海那条永远出局
   Python 层再按时效衰减重排：有效分 = sim × 0.5^(天数/180)
   │
   ▼
⑥ 归档遗忘（archiver.py:106 archive_expired）
   90 天冷分离：老会话导出 JSONL 再删；归档数据过保留期物理清除
```

配上 `save_turn` 的真实代码，三步流水线一目了然（memory_manager.py:89-117）：

```python
# 第1步·入库筛选
if self._filter_enabled and not self._should_memorize(user_query, llm_summary):
    return None                                  # 不值得记，直接不落库

# 第2步·落库：先拿到新行主键，第3步取代旧记忆要用它回填 superseded_by
history_id = self.pg.save_history(...)

# 第3步·冲突处理：新记忆已入库（id 已知）再取代旧的
if history_id and summary_embedding:
    conflict = self.pg.find_conflict_memory(
        summary_embedding, user_id, self._conflict_threshold,   # 默认 0.90
    )
    if conflict:
        self.pg.supersede_memory(conflict["id"], history_id)    # 旧的贴"已取代"
```

## 三、输入 → 处理 → 输出对照（本机实测）

### 3.1 入库筛选 `_should_memorize`（memory_manager.py:122）

```python
MemoryManager._should_memorize("你好")                # False（寒暄关）
MemoryManager._should_memorize("好的")                # False（长度关：2 < 4）
MemoryManager._should_memorize("？？？")              # False（内容关：纯标点）
MemoryManager._should_memorize("差旅报销标准是多少")    # True
MemoryManager._should_memorize("帮我算一下12*8")      # True
MemoryManager._should_memorize("你好，请问报销流程")   # True（不是整句寒暄——混在句中是正常表达）
```

处理逻辑（memory_manager.py:142-155）：

```python
q = (user_query or "").strip()
if len(q) < 4:
    return False                                       # ① 长度关
if re.sub(r"[，。！？!?.,~～\s]", "", q) == "":
    return False                                       # ③ 内容关（纯标点/空白）
# ② 寒暄关：整句（去标点空白后）等值命中才算寒暄
normalized = re.sub(r"[，。！？!?.,~～\s]", "", q).lower()
chitchat = {"你好", "您好", "嗨", "谢谢", "再见", "好的", "ok", ...}
return normalized not in chitchat
```

### 3.3 时效衰减（Python 层排序，memory_manager.py:311-324）

```python
# 两条记忆 similarity 都是 0.91：
#   A 写于今天      → 0.91 × 0.5^(0/180)   = 0.910  ← 排前面
#   B 写于 180 天前 → 0.91 × 0.5^(180/180) = 0.455
#   C 写于 360 天前 → 0.91 × 0.5^(360/180) = 0.228
```

真实代码（memory_manager.py:314-323）：

```python
def _effective(item: dict) -> float:        # 把一条记忆换算成"相似度 × 时效系数"
    t = item.get("time")
    days = (now - t).days if t else 0       # 时间缺失按 0 天 = 不衰减
    decay = 0.5 ** (max(days, 0) / self._half_life_days)
    return item["similarity"] * decay       # 有效分只喂排序，不写回 similarity

filtered.sort(key=_effective, reverse=True) # 又新又像的排前面
```

## 四、关键设计对照表：为什么是这么写

| 做法 | 原因（不这么写会怎样） |
|---|---|
| 筛选用规则不用 LLM | LLM 判"值不值得记"每次多一次调用、几百 ms 延迟；寒暄/过短/纯标点三关规则零成本全覆盖 |
| 整句匹配寒暄而非包含匹配 | "你好，请问报销流程"里也含"你好"，包含匹配会误杀带正事的问句 |
| 冲突阈值 0.90，比召回阈值 0.65 高很多 | 召回答"像不像"（宽进），冲突答"是不是同一件事"（严判）；0.65 会把"我住上海"和"我去上海出差"误判成冲突 |
| 先插新记忆、再废旧记忆 | 反过来（先废旧再插新）时插新失败，这个主题的记忆凭空消失；先插新最坏也只两条并存一轮 |
| 置 superseded 而非 DELETE | 真删了查无对证；置状态后 superseded_by 指向新条，"为什么模型改口了"可追溯 |
| 衰减只影响排序，不写回 similarity | 写回的话刚过 0.65 阈值的旧记忆会被误判成低置信，触发不该触发的人工审核 |
| COALESCE(memory_status,'active') | 老库升级瞬间的 NULL 行按 active 对待，与 ALTER DEFAULT 语义一致，不会整库召回为空 |
| 阈值全部配置化 | memory_filter_enabled / memory_conflict_threshold=0.90 / memory_recency_half_life_days=180 都在 config.py:123-125，改环境变量即生效，不用发版 |

## 五、用户隔离（已实现，面试常问）

```sql
-- pg_manager.py:778-783 长期召回
SELECT user_query, llm_summary, llm_full_answer,
       1 - (summary_embedding <=> %s) AS similarity, created_at
FROM chat_history
WHERE user_id = %s AND summary_embedding IS NOT NULL
  AND COALESCE(memory_status, 'active') = 'active'
ORDER BY summary_embedding <=> %s
LIMIT %s
```

短期记忆同样双条件：`WHERE session_id = %s AND user_id = %s`（pg_manager.py:697）。**所有记忆读写都带 user_id，A 的记忆对 B 在 SQL 层就不可见**——不是应用层过滤，是查询条件里写死的。

数据库侧的列定义（init_db.sql:45-46、80-83）：

```sql
memory_status      VARCHAR(16) DEFAULT 'active',   -- active 正常 / superseded 已被取代
superseded_by      BIGINT,                         -- 被哪条新记忆取代，可追溯
-- 老库升级：两列都是 ADD COLUMN IF NOT EXISTS，老行 NULL 按 active 对待
```

## 六、归档遗忘：为什么不能直接 DELETE

`archiver.py:106 archive_expired` 的流程：

```
list_expired_session_ids(90天)  →  逐会话导出 JSONL（先留证据）
        →  delete_sessions（chat_history 靠外键 ON DELETE CASCADE 连带删）
```

输入 → 输出对照：

```python
archive_expired(retention_days=90)
# 输出: {"ok": True, "retention_days": 90, "archived": 2, "deleted": 2,
#        "files": ["archives/2026-09-20/s-3f9c1a2b.jsonl", ...]}
```

直接 DELETE 最省事，但审计和争议回溯一定会问"半年前那次对话到底说了什么"。先落归档再删：PG 体积可控，证据也还在。注意归档数量不一致时只删已归档的（archiver.py:127-134），未归档的不删。

## 七、面试追问（附回答要点）

**Q1：冲突取代为什么不直接删旧记忆？**
要点：置 superseded 是软删，superseded_by 指向新条 id，"模型为什么改口"可回查；DELETE 是真删，出纠纷时查无对证。且召回 SQL 用 `COALESCE(memory_status,'active')='active'` 把 superseded 挡在结果外，软删达到了和删除一样的召回效果。

**Q2：新旧记忆的写入顺序为什么是先插新再废旧？**
要点：防"中间失败两边空"。若先废旧再插新，save_history 抛异常时旧记忆已被置 superseded、新的没进去，这个主题的记忆凭空消失。先插新的最坏情况只是新旧并存一轮，下一轮入库还会再查冲突（pg_manager.py:830 LIMIT 1 找最像的一条）。

**Q3：半衰期为什么选 180 天？**
要点：这是个业务拍脑袋值，关键不在数字在机制——"语义分相同时新者优先"。180 天覆盖大部分"用户偏好变化"的周期（换城市、换岗位）；太短（如 7 天）会把稳定的长期偏好也压没，太长（如 5 年）衰减形同虚设。配置项 `MEMORY_RECENCY_HALF_LIFE_DAYS` 可调。

**Q4：如果两个用户聊了完全相同的内容，会不会互相冲突取代？**
要点：不会。`find_conflict_memory` 的 SQL 有 `WHERE user_id = %s`（pg_manager.py:875），冲突检测只在同用户内进行；召回同样带 user_id。隔离是 SQL 条件写死的，不靠应用层自觉。

**Q5：时效衰减会不会让旧但正确的记忆被错误地"降权到召回不到"？**
要点：不会丢，只降排序。相似度阈值过滤（0.65）在衰减**之前**完成（memory_manager.py:254-257），衰减只影响 `filtered.sort` 的顺序，不写回 similarity 字段。top_k=5 是 SQL 层按原始相似度取的，衰减后只是队列内重排。

## 八、简单总结

1. 记忆问题的答案不在 embedding，在**生命周期五工序**：筛选（<4 字/寒暄/纯标点不入库）→ 隔离（SQL 强制 user_id）→ 冲突（≥0.90 旧的置 superseded，先插新再废旧）→ 时效（sim × 0.5^(天数/180) 只影响排序）→ 遗忘（90 天归档 + 保留期后物理删）
2. 三个关键数字：**0.90**（冲突阈值，远高于召回的 0.65）、**180 天**（半衰期）、**90 天**（冷热分离线）
3. 最大的坑是"新旧并存都召回"造成的**模型自相矛盾**——治它靠状态列而不是删数据，删了就查无对证
