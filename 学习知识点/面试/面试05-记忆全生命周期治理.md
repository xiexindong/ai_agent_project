# 面试05：向量记忆的筛选、冲突、时效、遗忘、隔离，怎么治理？

> 配套代码：`modules/memory/memory_manager.py:53-156`（save_turn 治理流水线）、`modules/memory/pg_manager.py:778、823`（新增冲突方法）、`init_db.sql`（memory_status 列）、`modules/memory/archiver.py`
> 一句话结论：**这些问题 90% 不是 embedding 的错，是记忆架构缺"生命周期管理"——本项目补齐了五道工序：入库筛选（挡噪声）→ 用户隔离（user_id 过滤）→ 冲突处理（新取代旧）→ 时效衰减（180 天半衰期）→ 归档遗忘（90 天冷分离 + 物理清除）。**

---

## 一、先说结论：五大问题 × 五道工序

| 问题 | 根因 | 工序 | 代码位置 |
|---|---|---|---|
| 无效/玩笑内容入库 | 入库无门槛 | 入库筛选 `_should_memorize` | memory_manager.py:122 |
| 遗忘关键信息 | 长期召回只有相似度 | 时效衰减重排（180 天半衰） | memory_manager.py:303 |
| 记忆互相矛盾 | 新旧并存都被召回 | 冲突取代（≥0.90 旧的置 superseded） | pg_manager.py:778、823 |
| 时效性失效 | 只有 created_at 没有状态 | 衰减 + superseded 状态列 | init_db.sql memory_status |
| 脏记忆难清理 | 只敢软删 | 归档→保留期→物理删 | archiver.py / purge_archived_data |
| 跨用户泄露 | 召回 SQL 不带 user_id | 所有读写强制 user_id 过滤 | pg_manager.py:712 |

## 二、大白话拆解：一条记忆的一生

```
用户说 "我搬到北京了"
   ↓
① 入库筛选 _should_memorize（memory_manager.py:122）
   长度关(<4字拦) → 寒暄关(整句="你好"拦) → 内容关(纯标点拦)
   "你好" 在这里就死了，根本不落库
   ↓
② 落库 save_history（pg_manager.py:524）
   原文+摘要+双向量+工具日志 一行写入，拿回 id=57
   ↓
③ 冲突检测 find_conflict_memory（pg_manager.py:778）
   用新摘要向量在同用户 active 记忆里找 ≥0.90 的
   → 命中 id=40 "用户住址:上海"（sim=0.93）
   ↓
④ 冲突取代 supersede_memory（pg_manager.py:823）
   UPDATE id=40 SET memory_status='superseded', superseded_by=57
   （不物理删——留审计痕迹）
   ↓
⑤ 未来某天被召回时（search_memory_by_vector）
   SQL 只取 COALESCE(memory_status,'active')='active'  → 上海那条永远出局
   排序按时效衰减：sim × 0.5^(天数/180)
   ↓
⑥ 归档遗忘（archiver.py + purge_archived_data）
   90 天冷分离：老会话导出 JSONL 再删；归档数据过保留期物理清除
```

## 三、输入 → 输出对照（入库筛选本机实测）

```python
MemoryManager._should_memorize("你好")                # False（寒暄关）
MemoryManager._should_memorize("好的")                # False（长度关：2 < 4）
MemoryManager._should_memorize("？？？")              # False（内容关：纯标点）
MemoryManager._should_memorize("差旅报销标准是多少")    # True
MemoryManager._should_memorize("帮我算一下12*8")      # True
MemoryManager._should_memorize("你好，请问报销流程")   # True（不是整句寒暄——混在句中是正常表达）
```

```python
# 冲突处理（SQL 层）
# 输入: 新记忆 "用户住址:北京"(向量V2), user_id="cli-user", threshold=0.90
# 库内: id=40 "用户住址:上海"(active) 与 V2 相似度 0.93
find_conflict_memory(V2, "cli-user", 0.90)
# 输出: {"id": 40, "summary": "用户住址:上海", "similarity": 0.93}

supersede_memory(40, 57)
# 执行: UPDATE chat_history SET memory_status='superseded', superseded_by=57
#       WHERE id=40 AND memory_status='active'
# 输出: True；重复调用输出 False（已是 superseded，幂等）

# 时效衰减（Python 层排序）
# 两条记忆 similarity 都是 0.91：
#   A 写于今天    → 0.91 × 0.5^(0/180)   = 0.910  ← 排前面
#   B 写于 360 天前 → 0.91 × 0.5^(360/180) = 0.228
```

## 四、为什么要这么写

| 做法 | 原因（不这么写会怎样） |
|---|---|
| 筛选用规则不用 LLM | LLM 判"值不值得记"每次多一次调用、几百 ms 延迟；寒暄/过短/纯标点三关规则零成本全覆盖 |
| 整句匹配寒暄而非包含匹配 | "你好，请问报销流程"里也含"你好"，包含匹配会误杀带正事的问句 |
| 冲突阈值 0.90，比召回阈值 0.65 高很多 | 召回答"像不像"（宽进），冲突答"是不是同一件事"（严判）；0.65 会把"我住上海"和"我去上海出差"误判成冲突 |
| 先插新记忆、再废旧记忆 | 反过来（先废旧再插新）时插新失败，这个主题的记忆凭空消失；先插新最坏也只两条并存一轮 |
| 置 superseded 而非 DELETE | 真删了查无对证；置状态后 superseded_by 指向新条，"为什么模型改口了"可追溯 |
| 衰减只影响排序，不写回 similarity | 写回的话刚过 0.65 阈值的旧记忆会被误判成低置信，触发不该触发的人工审核 |
| COALESCE(memory_status,'active') | 老库升级瞬间的 NULL 行按 active 对待，与 ALTER DEFAULT 语义一致，不会整库召回为空 |

## 五、用户隔离（已实现，面试常问）

```sql
-- pg_manager.py:712 长期召回
WHERE user_id = %s AND summary_embedding IS NOT NULL
  AND COALESCE(memory_status, 'active') = 'active'
ORDER BY summary_embedding <=> %s
```

短期记忆同样双条件：`WHERE session_id = %s AND user_id = %s`（pg_manager.py:646）。**所有记忆读写都带 user_id，A 的记忆对 B 在 SQL 层就不可见**——不是应用层过滤，是查询条件里写死的。

## 六、简单总结

1. 记忆问题的答案不在 embedding，在**生命周期五工序**：筛选（<4 字/寒暄/纯标点不入库）→ 隔离（SQL 强制 user_id）→ 冲突（≥0.90 旧的置 superseded，先插新再废旧）→ 时效（sim × 0.5^(天数/180) 只影响排序）→ 遗忘（90 天归档 + 保留期后物理删）
2. 三个关键数字：**0.90**（冲突阈值，远高于召回的 0.65）、**180 天**（半衰期）、**90 天**（冷热分离线）
3. 最大的坑是"新旧并存都召回"造成的**模型自相矛盾**——治它靠状态列而不是删数据，删了就查无对证
