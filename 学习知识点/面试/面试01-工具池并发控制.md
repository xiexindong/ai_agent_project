# 面试01：同一个工具实例，为什么能被多个任务并发调用？

> 配套代码：`modules/tools/concurrency.py`（新增实现）、`modules/tools/tool_registry.py:93、349`、`modules/harness/middleware.py:208`、`modules/multiagent/harness.py:836`
> 一句话结论：**能并发的前提是工具实例"可重入"（无状态、不锁死自己）；框架层面用「信号量闸门限并发 + 实例池隔离有状态工具」两件套，把 N 个并发请求安全地喂给同一个（或一组）工具实例。**

---

## 一、先说结论

| 面试问 | 一句话答 |
|---|---|
| 同一实例为什么能并发？ | 实例本身无状态（纯函数型），多线程进同一个实例互不干扰 |
| 那还要什么并发控制？ | 实例不崩不代表下游不崩——DB、MCP 子进程、外部 API 会被并发打爆 |
| 控制在哪做？ | `ToolConcurrencyGuard`：每工具名一把信号量，同时最多 4 个在执行，超出的排队 |
| 有状态工具怎么办？ | `ToolInstancePool`：借出-归还，每个线程拿专属实例，从根上消除状态串台 |
| 排进链路的位置？ | `execute_tool` 第②步：闸门包住重试，重试包住执行 |

---

## 二、大白话拆解：两件套各管什么

| 部分 | 大白话解释 |
|---|---|
| `ToolConcurrencyGuard` | 每个工具名发一张"通行证桌"，桌上有 4 个牌子，拿到牌子的才能执行，没拿到的在门口排队 |
| `threading.Semaphore(4)` | 就是那 4 个牌子：acquire 拿牌子，release 还牌子 |
| `self._in_flight` | 账本：现在有几个人在屋里（观测用） |
| `self._max_seen` | 账本：历史上最多同时几个人在屋（压测看它，长期等于 4 说明排队常发生） |
| `ToolInstancePool.checkout()` | 从池里借一个工具实例，池空了就等别人还 |
| `ToolInstancePool.checkin()` | 用完还回去，还唤醒在等的线程 |
| `borrow()` 上下文管理器 | `with pool.borrow() as t:` 块结束自动还，块里抛异常也不泄漏 |
| `Condition` | 池空时的"等待-唤醒"机制：没有空闲实例就睡觉，有人 checkin 就被叫醒 |

## 执行链路全景

```
LLM 给出 tool_calls
   ↓
ToolRegistry.execute_tool (tool_registry.py:220)
   ├── 存在性检查 get_tool(name)
   ├── ① Harness 五道中间件（参数/权限/范围/限流/预算）
   ├── 限次（单工具 ≤ 5 次） + 同参去重（命中缓存直接回传）
   ├── ② 并发闸门 ToolConcurrencyGuard          ← 新增，tool_registry.py:349
   │      └── 重试 ToolRetryPolicy               ← 新增（见面试03）
   │             └── 真正执行 harness.execute / tool.run()
   └── ③ 结果过滤（裁剪+脱敏）+ 缓存
```

顺序是**闸门包住重试**：每一次重试尝试都占一个并发名额，不会出现"排队名额被重试绕过"。

## 三、输入 → 输出对照（本机实测）

```python
# 实测脚本：2 个名额，4 个线程同时调同一个工具
guard = ToolConcurrencyGuard(max_concurrent=2)
ts = [threading.Thread(target=lambda: guard.execute("calc", work)) for _ in range(4)]
# work 内部记录"当前同时执行数"

# 运行结果:
# guard: peak=2 done=4    ← 4 个请求全部完成，但任意时刻同时在执行 ≤ 2
```

```python
# 实例池实测：池大小 2
pool = ToolInstancePool(factory=lambda: object(), size=2)
a = pool.checkout()      # 借到实例 #1
b = pool.checkout()      # 借到实例 #2
pool.checkout(timeout=0.1)
# 运行结果: TimeoutError —— 两个实例都在外，第三个借不到（等待 0.1s 超时）
pool.checkin(a)          # 还回 #1
c = pool.checkout()      # 立刻借到刚还回来的 #1
```

## 四、为什么要这么写

| 做法 | 原因（不这么写会怎样） |
|---|---|
| 信号量默认 4（`TOOL_MAX_CONCURRENT`） | 不设上限时 20 个线程同时进 calculator，下游 DB 连接池 5 个连接直接被排队打死 |
| acquire 超时 30 秒 | 不设超时会无限等：下游全挂时所有线程永远卡在门口，整站不可用 |
| 实例池 `size` 保底 1（`max(1, ...)`） | 传 0 会让池子永远空、永远借不到、每次都超时——等于全站拒绝服务 |
| checkin 放 `finally` | 块里抛异常不还实例：池永久缩容，借一个少一个，最后全超时 |
| `release` 引用计数归零才断开 | A 刚退出就断连接，B 还在用——B 的下一次调用直接 Connection reset |
| 在途/峰值两张账 | 不记账就说不清"到底有没有发生并发"；峰值长期=上限是加名额/加实例的量化依据 |
| 有状态工具用池、无状态用闸门 | 闸门治不了状态串台：共享游标被两个线程 execute，A 的结果集被 B 顶掉，A fetchall 拿到 B 的数据且**不报错** |

---

## 五、等价写法：框架层面的其他选择

| 方案 | 本项目为什么不用 |
|---|---|
| 每次调用 new 一个工具实例 | 有连接成本的工具（MCP 子进程）每次拉起一个进程，延迟秒级 |
| `asyncio.Semaphore`（协程信号量） | 项目执行层是同步 + `ThreadPoolExecutor`（multiagent/harness.py:836），线程信号量才对路 |
| 全局一把大锁（串行化一切） | 安全但吞吐归零：所有工具共享一个队列，calculator 也要等 web_search 跑完 |

---

## 六、简单总结

1. 并发的合法性来自**实例可重入**（无状态）；工程必要性来自**下游有承受上限**，所以闸门默认每工具 4 个并发、排队上限 30 秒
2. 无状态工具过**闸门**（tool_registry.py:349），有状态工具过**实例池**（借出-归还，`finally` 保证归还）
3. 最大的坑是**静默串台**：共享实例的状态被覆盖不报错，池化从根上消除；忘记 release/checkin 则会让池/会话永久缩容
