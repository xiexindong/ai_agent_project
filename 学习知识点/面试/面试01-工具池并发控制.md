# 面试01：同一个工具实例，为什么能被多个任务并发调用？

> 配套代码：`modules/tools/concurrency.py`（闸门+实例池实现）、`modules/tools/tool_registry.py:226`（execute_tool 入口）、`modules/harness/harness.py:390-396`（闸门/重试接线处）、`modules/harness/middleware.py:208`（限流中间件）、`modules/multiagent/harness.py:837`（多 Agent 线程池）
> 一句话结论：**能并发的前提是工具实例"可重入"（无状态、不锁死自己）；框架层面用「信号量闸门限并发 + 实例池隔离有状态工具」两件套，把 N 个并发请求安全地喂给同一个（或一组）工具实例。**

---

## 〇、面试官视角与 30 秒回答

**面试官到底想问什么**：不是考你背 Semaphore 的 API，而是想确认你知道两件事——①"同一实例被多线程调"什么时候安全、什么时候会出鬼；②工程上怎么把"并发"关进笼子里（限流）又不至于"串台"（隔离）。

**30 秒回答模板**：

> "工具能不能并发，先看它有没有状态。像 calculator 这种纯计算工具，入参决定一切、实例上不留任何痕迹，多个线程同时进同一个实例也互不干扰，天然可重入。但'实例扛得住'不等于'下游扛得住'——数据库连接池、MCP 子进程、外部 API 都有承受上限，所以我在执行链路里加了一个信号量闸门 `ToolConcurrencyGuard`：同名工具同时最多 4 个在执行，超出的排队 30 秒，保下游不被打爆。而对有状态的工具——比如身上挂着数据库游标的——闸门治不了'结果集被顶掉'这种静默串台，这类工具走 `ToolInstancePool` 实例池：每个线程借走自己的实例，用完归还，从根上消除共享状态。位置在 harness 的 execute 里：闸门包住重试、重试包住真执行。"

**术语首次出现的大白话**：

| 术语 | 大白话 |
|---|---|
| 可重入（reentrant） | 一间自助拍照亭：里面不留上一个人的东西，谁进去拍都一样——这样的代码多少线程同时进都没事。 |
| 无状态（stateless） | 计算器：你按 `3*7` 永远是 21，跟上一个人按过什么没关系。 |
| 有状态（stateful） | 翻页的纸质书：你看到第几页取决于上一个翻书的人停在哪——别人一翻，你的"当前页"就变了。 |
| 信号量（Semaphore） | 停车场的余位计数牌：进来一辆减 1，减到 0 后来的车排队；出去一辆加 1，放一辆排队的进来。 |
| 实例池（Instance Pool） | 共享单车池：扫码借车，骑完还车，车不够就等别人还——每个人骑走的都是独立的一辆。 |

## 一、先说结论

| 面试问 | 一句话答 |
|---|---|
| 同一实例为什么能并发？ | 实例本身无状态（纯函数型），多线程进同一个实例互不干扰 |
| 那还要什么并发控制？ | 实例不崩不代表下游不崩——DB、MCP 子进程、外部 API 会被并发打爆 |
| 控制在哪做？ | `ToolConcurrencyGuard`：每工具名一把信号量，同时最多 4 个在执行，超出的排队 |
| 有状态工具怎么办？ | `ToolInstancePool`：借出-归还，每个线程拿专属实例，从根上消除状态串台 |
| 排进链路的位置？ | Harness `execute` 里：闸门包住重试，重试包住执行（harness/harness.py:390-396） |

## 二、大白话拆解：两件套各管什么

| 部分 | 大白话解释 |
|---|---|
| `ToolConcurrencyGuard` | 每个工具名发一张"通行证桌"，桌上有 4 个牌子，拿到牌子的才能执行，没拿到的在门口排队 |
| `threading.Semaphore(4)` | 就是那 4 个牌子：acquire 拿牌子，release 还牌子 |
| `self._in_flight` | 账本：现在有几个人在屋里（观测用） |
| `self._max_seen` | 账本：历史上最多同时几个人在屋（压测看它，长期等于 4 说明排队常发生） |
| `ToolInstancePool.checkout()` | 从池里借一个工具实例，池空了就等别人还 |
| `ToolInstancePool.checkin()` | 用完还回去，还唤醒在等的线程 |
| `borrow()` 上下文管理器 | `with pool.borrow() as t:` 块结束自动还，块里抛异常也不泄漏 |
| `Condition` | 池空时的"等待-唤醒"机制：没有空闲实例就睡觉，有人 checkin 就被叫醒 |

**一句话分清两件套的分工**（面试高频加分点）：闸门管"**进几个人**"，实例池管"**进来之后用哪张桌子**"。所以闸门防的是下游被打爆（人太多挤垮房子），防不了实例内状态串台（抢桌子）；防抢桌子的只有池。

### 执行链路全景（锚点已按当前代码核实）

```
LLM 给出 tool_calls
   ↓
ToolRegistry.execute_tool (tool_registry.py:226)
   ├── 存在性检查 get_tool(name)                    (tool_registry.py:290)
   ├── ① Harness 五道中间件（参数/权限/范围/限流/预算） (harness.py before_call → middleware.py)
   ├── 限次（单工具 ≤ 5 次） + 同参去重（命中缓存直接回传）  (tool_registry.py:342、355)
   └── ⑥ harness.execute(tool, params, cap)         (tool_registry.py:375)
          ├── ② 并发闸门 ToolConcurrencyGuard        ← harness/harness.py:393（guard.execute 包住内层）
          │      └── 重试 ToolRetryPolicy            ← harness/harness.py:387（见面试03-工具错误篇）
          │             └── 真正执行 runner.run() / tool.run()
          └── 排队 30s 超时也转成失败 ToolResult，不抛异常（harness/harness.py:394-396）
   └── ③ 结果过滤（裁剪+脱敏）+ 缓存                 (tool_registry.py:386-391)
```

顺序是**闸门包住重试**：每一次重试尝试都占一个并发名额，不会出现"排队名额被重试绕过"。接线处在 `build_tool_harness`（harness/harness.py:585-590）：闸门默认上限 4（`tool_max_concurrent`），重试默认 2 次、退避 0.5 秒起。

真实代码（闸门包住重试的分层，harness/harness.py:380-396）：

```python
def _run_once() -> ToolResult:
    return runner.run(tool, call_params, timeout)          # 最内层：真执行一次

def _run_with_retry() -> ToolResult:
    if self.retry is None:
        return _run_once()
    return self.retry.run(tool_name, _run_once)            # 中间层：瞬时故障重试

if self.guard is None:
    return _run_with_retry()
try:
    return self.guard.execute(tool_name, _run_with_retry)  # 最外层：闸门包整趟
except TimeoutError as e:
    return ToolResult(success=False, error=str(e), meta={"code": "concurrency_timeout"})
```

## 三、核心概念：输入 → 处理 → 输出 对照

### 例子 1：并发闸门（无状态工具 calculator）

```python
guard = ToolConcurrencyGuard(max_concurrent=2)

def work():
    # 模拟一次工具执行，内部记录"当前同时执行数"
    return guard.execute("calc", real_calc)

ts = [threading.Thread(target=work) for _ in range(4)]
```

| 阶段 | 输入 | 处理（闸门内部） | 输出 / 状态 |
|---|---|---|---|
| t1、t2 到达 | `guard.execute("calc", fn)` ×2 | 信号量计数 2→1→0，两个都拿到名额 | 2 个线程同时执行，在途=2 |
| t3、t4 到达 | 同上 ×2 | 信号量计数已是 0，减不动 → 门口排队 | 阻塞等待（最多 30s），在途仍=2 |
| t1 执行完 | fn 返回 | `finally` 里计数 0→1，放行一个排队者 | t3 立刻拿到名额开始执行，在途回到 2 |
| 全部结束 | — | 账实相符 | `guard: peak=2 done=4` —— 4 个请求全部完成，但任意时刻同时在执行 ≤ 2 |

真实代码（闸门核心，concurrency.py:138-152）：

```python
def execute(self, name: str, fn: Callable[[], Any]) -> Any:
    sem = self._semaphore(name)            # 拿这把工具的闸门（第一次用则现造）
    acquired = sem.acquire(timeout=30)     # 最多等 30 秒
    if not acquired:
        raise TimeoutError(f"工具 {name} 并发排队超时(30s)，当前在途 {self.in_flight(name)}")
    try:
        with self._lock:                   # 在途数 +1（观测用）
            cur = self._in_flight.get(name, 0) + 1
            self._in_flight[name] = cur
            self._max_seen[name] = max(self._max_seen.get(name, 0), cur)
        return fn()                        # 真正执行（成功或抛异常都算"这一趟结束"）
    finally:
        with self._lock:
            self._in_flight[name] = self._in_flight.get(name, 1) - 1
        sem.release()                      # 还名额：排在后面的线程立刻顶上
```

### 例子 2：实例池（有状态工具，池大小 2）

```python
pool = ToolInstancePool(factory=lambda: object(), size=2)
```

| 阶段 | 输入 | 处理（池内部） | 输出 / 状态 |
|---|---|---|---|
| 第一次借 | `pool.checkout()` | `_idle` 空、没造满 → 调 factory 现造 #1 | 借到实例 #1 |
| 第二次借 | `pool.checkout()` | 同上，现造 #2（造满） | 借到实例 #2 |
| 第三次借 | `pool.checkout(timeout=0.1)` | `_idle` 空且已造满 → `Condition.wait` 睡觉等归还 | 0.1s 没人还 → 抛 TimeoutError |
| 还 #1 | `pool.checkin(a)` | `append` 回空闲栈 + `notify_all` 喊醒等待者 | `_idle=[#1]` |
| 第四次借 | `pool.checkout()` | 栈里有货直接 `pop` | 立刻借到刚还回来的 #1，零创建成本 |

真实代码（借出三分支，concurrency.py:250-273）：

```python
def checkout(self, timeout: float = 10.0) -> Any:
    with self._available:
        deadline = time.time() + timeout
        while True:
            if self._idle:
                return self._idle.pop()                  # ① 有空闲：直接复用，零创建成本
            if self._created < self._size:
                self._created += 1
                instance = self._factory()               # ② 没空闲但没造满：现造一个
                self._available.notify_all()
                return instance
            remaining = deadline - time.time()
            if remaining <= 0 or not self._available.wait(remaining):
                raise TimeoutError(                      # ③ 造满了且等到超时：拒绝
                    f"工具实例池 {self._name} 借出超时({timeout}s)："
                    f"上限 {self._size} 个实例全部在用")
```

**注意**：`ToolInstancePool` 当前是"造好的通用件"，装配注释里写明尚未接线（concurrency.py:196-199）——面试时被问"线上用了吗"要如实回答：闸门已在 harness 链路生效（harness/harness.py:393），池是有状态工具接入时的备选方案，测试和压测脚本里在用。

## 四、为什么要这么写

| 做法 | 原因（不这么写会怎样） |
|---|---|
| 信号量默认 4（`tool_max_concurrent`，harness/harness.py:586） | 不设上限时 20 个线程同时进 calculator，下游 DB 连接池 5 个连接直接被排队打死 |
| acquire 超时 30 秒（concurrency.py:140） | 不设超时会无限等：下游全挂时所有线程永远卡在门口，整站不可用 |
| 实例池 `size` 保底 1（`max(1, ...)`，concurrency.py:220） | 传 0 会让池子永远空、永远借不到、每次都超时——等于全站拒绝服务 |
| checkin 放 `finally`（concurrency.py:302-303） | 块里抛异常不还实例：池永久缩容，借一个少一个，最后全超时 |
| release 引用计数归零才断开 | A 刚退出就断连接，B 还在用——B 的下一次调用直接 Connection reset |
| 在途/峰值两张账（concurrency.py:124-125） | 不记账就说不清"到底有没有发生并发"；峰值长期=上限是加名额/加实例的量化依据 |
| 有状态工具用池、无状态用闸门 | 闸门治不了状态串台：共享游标被两个线程 execute，A 的结果集被 B 顶掉，A fetchall 拿到 B 的数据且**不报错** |

## 五、关键设计对照表：方案 A / B / C 怎么选

### 5.1 三种并发处置方案对比

| | 方案 A：全局一把大锁 | 方案 B：信号量闸门（本项目） | 方案 C：每次调用 new 实例 |
|---|---|---|---|
| 思路 | 所有工具共用一个队列，串行执行 | 同名工具最多 4 个并行，超出排队 | 每请求新建一个实例，用完即弃 |
| 安全性 | 最高（串行化一切） | 下游受保护；实例内状态仍需无状态保证 | 天然隔离 |
| 吞吐 | 归零：calculator 也要等 web_search 跑完 | 高：不同工具互不阻塞，同工具最多 4 路 | 高，但延迟被创建成本拖垮 |
| 致命伤 | 吞吐归零 | 救不了有状态工具（串台） | 有连接成本的工具（MCP 子进程）每次拉起进程，延迟秒级 |
| 本项目取舍 | 不用 | **无状态工具的默认方案** | 不用；有状态工具用池（预先造好 N 个复用） |

### 5.2 框架层面的其他等价写法

| 方案 | 本项目为什么不用 |
|---|---|
| `asyncio.Semaphore`（协程信号量） | 项目执行层是同步 + `ThreadPoolExecutor`（multiagent/harness.py:837），线程信号量才对路；混用协程信号量等于在错误的世界线上排队 |
| 无锁 + 原子计数器 | Python 的 GIL 不保证复合操作原子性（`count += 1` 是读-改-写三步），还是得加锁，不如直接用标准库 Semaphore |
| 消息队列排队调用 | 单体进程内引入 MQ 是杀鸡用牛刀；跨机器场景才值得（见面试03-多Agent三大技术方案） |

## 六、面试话术（可直接背）

**开场 30 秒**：见本文「〇、面试官视角与 30 秒回答」。

**被追问时的铺陈话术**：

> "并发控制的本质是回答两个问题：**多少个可以一起跑**（闸门回答：同名最多 4 个），**一起跑会不会互相踩**（无状态则不会，有状态则池化隔离）。本项目把这两个问题拆给了两个组件：闸门放在 harness 执行层包住重试和真执行，保证每一趟在途只占一个名额；池是通用件，哪个工具有状态就给哪个工具配一个，借出-归还用 `with` 保证异常路径也不泄漏。"

**收口话术**：

> "这套设计里最深的坑不是崩溃，而是**静默串台**——共享游标被顶掉时不报任何错，数据悄悄串了。所以我的原则是：能无状态就无状态，不得不有状态就池化，绝不用'大家都小心点'来防并发。"

## 七、高频追问（含回答要点）

**Q1：信号量默认 4 是怎么定的？怎么知道要调大？**
- 要点：4 是经验值，对齐典型下游（DB 连接池 5）留一档余量；
- 量化依据是 `max_seen` 峰值账本：**峰值长期等于上限 = 排队常发生**，该加名额或加实例了；
- 排队超时（30s）报错增多也是信号，但先于报错看峰值曲线更主动。

**Q2：为什么闸门管不了有状态工具？**
- 要点：闸门账本上只记"进来了几个人"，对屋里谁在写 `self` 一无所知；
- 串台发生在 execute 和 fetchall 两步之间的时间缝里，上限设成 4 仍可能 2 个线程交错；
- 把上限压到 1（全程串行）能防串台但吞吐归零，正解是池化各借各的实例（一个连接可以开多个游标，天然不串）。

**Q3：重试放在闸门里面还是外面？为什么？**
- 要点：本项目是闸门包住重试（harness/harness.py:393），每一次重试尝试都占一个并发名额；
- 反过来的漏洞：排队名额被重试绕过——一个线程占着名额反复重试，门外排队的永远进不来，相当于给重试开了绿色通道，限流失效。

**Q4：多 Agent 并发时，并发是从哪来的？**
- 要点：多 Agent 编排用 `ThreadPoolExecutor` 按批并行跑任务（multiagent/harness.py:837，线程数=配置上限与任务数取小）；
- N 个 Agent 同时调同名工具 → 最终汇到同一个 `ToolConcurrencyGuard` 的信号量上排队；
- 所以闸门是"全局每工具一把"，不是每个 Agent 一把——这才是保护下游的正确粒度。

**Q5：如果工具每次执行都要新建数据库连接，闸门还有意义吗？**
- 要点：有——闸门限的是"同时在执行的请求数"，恰好把"同时在建的连接数"也限制在上限内，保护数据库；
- 但新建连接成本高，更优组合是：闸门限并发 + 连接池（或 ToolInstancePool）复用实例，两者解决不同问题（一个限流，一个省创建成本）。

**Q6：排队 30 秒超时后用户看到什么？**
- 要点：harness 把 `TimeoutError` 转成失败 ToolResult（`meta.code="concurrency_timeout"`，harness/harness.py:394-396），不向上抛异常；
- 失败原因回喂模型，模型会收到"并发排队超时"的中文原因，可以决定稍后重试或换工具——对用户表现为一次可解释的失败，而不是卡死。

## 八、简单总结

1. 并发的合法性来自**实例可重入**（无状态）；工程必要性来自**下游有承受上限**，所以闸门默认每工具 4 个并发、排队上限 30 秒
2. 无状态工具过**闸门**（接线在 harness/harness.py:393，装配在 585-590），有状态工具过**实例池**（借出-归还，`finally` 保证归还）
3. 最大的坑是**静默串台**：共享实例的状态被覆盖不报错，池化从根上消除；忘记 release/checkin 则会让池/会话永久缩容
4. 面试答题主线一句话：**"先分有状态/无状态，无状态用闸门限流保下游，有状态用实例池隔离防串台，重试必须被闸门包住。"**
