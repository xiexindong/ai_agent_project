# 面试10：长期记忆只存 summary，短期对话却 [:200] 粗暴截断？

> 配套代码：`modules/memory/memory_manager.py:404-416`（_format_context）、`memory_manager.py:382-399`（_compress_long_term）、`modules/memory/pg_manager.py:566`（save_history 存什么）、`config.py:118`（short_memory_rounds=3）、`config.py:113`（max_history_tokens=4000）
> 一句话结论：**两套压缩策略对应两种数据形态——久远历史"存的时候就已经压缩"（入库前生成一句话摘要，召回即用），近期对话"存原文、用的时候按预算截断"（前 200 字符），因为近期对话的细节（指代、上下文）在当轮还有用，提前压缩会把"它""那个"压成废话。**

---

## 〇、名词先扫盲（大白话版）

| 术语 | 大白话解释 |
|---|---|
| **长期记忆** | 像"读书笔记"：很久以前聊过的事，只记一句精华（"用户是财务岗"），原话早扔了。跨会话有效 |
| **短期记忆** | 像"刚才的聊天记录"：当前会话最近几轮的原话，一字不动。只管这次对话 |
| **summary（摘要）** | 一轮对话压成的一句话，入库时就由模型生成好（pg_manager.py:566 save_history 的 `llm_summary` 列） |
| **截断 [:200]** | Python 切片：字符串只留前 200 个字符，后面全砍。零成本、零延迟 |
| **token 预算** | 塞给模型的上下文有长度上限（按 token 计费/限量），超了要么裁剪要么压缩。记忆栏预算是 4000 token（config.py:113） |
| **指代/代词** | "那它呢？""这个怎么弄"里的"它""这个"——必须看到上一句原文才知道指谁。这是短期记忆必须留原文的根本原因 |

## 一、先说结论

| 面试问 | 一句话答 |
|---|---|
| 长期为什么用摘要？ | 入库时 LLM 已生成一句话 summary，原文几千 token 摘要几十字；久远历史只需要"记得大概" |
| 短期为什么截断？ | 近期对话要求"逐字准"（代词、追问都靠原文），但 token 预算有限，AI 回答砍到前 200 字符 |
| [:200] 不粗暴吗？ | 粗暴但可控：3 轮 × 200 字 ≈ 600 字封顶；生产可换摘要生成，但每次多一轮 LLM 调用 |
| 截断丢关键信息怎么办？ | 上下文溢出有第二道闸：token 超 `max_history_tokens=4000` 触发 `_compress_long_term` 合并久远摘要（memory_manager.py:201-205） |

## 二、大白话拆解：两种压缩长什么样

**压缩策略 A：长期记忆"存时压"**——入库那天就压好，用时零成本：

```
一轮对话结束 → save 节点 → SummaryGenerator 生成一句话摘要
→ pg_manager.py:566 save_history 把【原文 + 摘要 + 摘要向量】一起落库
→ 日后召回时只读 summary 列，原文永远不进出 prompt
```

**压缩策略 B：短期记忆"用时压"**——原文原样存，喂给模型前才砍：

```python
# memory_manager.py:404-416（_format_context）
@staticmethod
def _format_context(long_term: list, short_term: list, query: str) -> str:
    """拼接记忆上下文为文本。"""
    blocks = []
    if long_term:
        blocks.append("【历史记忆摘要】")
        for item in long_term:
            blocks.append(f"- {item.get('summary', '')}")          # ① 长期：只拼 summary
    if short_term:
        blocks.append("\n【近期对话】")
        for item in short_term:
            blocks.append(f"用户: {item.get('query', '')}")        # ② 用户问句：原样全文
            blocks.append(f"AI: {item.get('answer', '')[:200]}")   # ③ AI 回答：砍到前 200 字
    return "\n".join(blocks)
```

| 部分 | 大白话解释 |
|---|---|
| `item.get('summary', '')` | 久远记忆只取摘要——入库那天就已经压好了，这里直接用 |
| `item.get('answer', '')[:200]` | 近期回答切片：只留前 200 个字符，后面全砍 |
| 用户问句不截断 | 问句本来短；且追问往往就一句话（"那它呢"），砍了就断线 |
| `get(键, '')` | 字段缺失兜底成空串，不会 KeyError |

**第二道闸：整体溢出后的合并压缩**（memory_manager.py:201-205 + 382-399）：

```
_format_context 拼完 → check_token_overflow(text, 4000) 超了？
   ↓ 超
_compress_long_term：把长期召回的多条摘要交给 SummaryGenerator 合并成一条
   ↓
重新 _format_context 拼一遍，compressed=True 返回（前端可提示"历史已压缩"）
   ↓ 合并失败（LLM 异常）
原样返回——宁可超也不丢内容（memory_manager.py:390-391）
```

## 四、关键设计对照表

| 维度 | 长期记忆（存时压） | 短期记忆（用时压） |
|---|---|---|
| 压缩时机 | 入库前（save 节点生成摘要） | 喂 prompt 前（[:200] 切片） |
| 压缩手段 | LLM 生成一句话摘要 | Python 切片，零成本 |
| 原文去哪了 | 存 chat_history 但召回时不读 | 原文进 prompt（回答截 200 字） |
| 每次使用成本 | 零（读现成的） | 零（切片不算成本） |
| 保什么 | 语义主旨（"大概是这么回事"） | 字面细节（代词、追问能接上） |
| 失效场景 | 需要原文细节时不够用 | 轮次多了装不下（固定 3 轮） |

---

## 五、为什么要这么写

| 做法 | 原因（不这么写会怎样） |
|---|---|
| 长期"入库即压缩" | 用的时候才压缩：每次召回都要先拉原文（几千 token 白传）再调一次 LLM 摘要，延迟和费用翻倍 |
| 短期存原文 | 入库时也压成摘要："那它呢？→ 主题: 烤鸭"——下一轮模型根本不知道"它"指什么，追问全断线 |
| 截 [:200] 而非摘要 | 摘要每轮多一次 LLM 调用（几百 ms + 费用）；截断零成本，且 200 字通常覆盖结论部分（答案结构：结论在前，展开在后） |
| 用户问句完整保留 | 问句是语义锚点（"那烤鸭呢"必须逐字在），砍问句等于砍掉对话的线 |
| 溢出有第二道闸 | 光截断不够时（长期召回很多），`check_token_overflow` 超 4000 token 触发 `_compress_long_term` 把多条久远摘要合成一条 |
| 合并失败原样返回 | `_compress_long_term` 里 `if not merged: return long_term`（memory_manager.py:390-391）——LLM 挂了宁可超预算也不丢记忆 |

## 六、可能的追问与回答要点

**Q1：[:200] 会不会刚好把关键数字砍掉？**
答：会有概率，所以它是"预算友好的近似"而非完美方案。缓解手段：① 本项目 prompt 要求答案"结论在前"（summary 标签也在末尾单独入库），前 200 字大概率含结论；② 真有细节需求，短期记忆旁边还有长期摘要和 RAG 栏补；③ 生产可换成"按句号截断"或"小模型再摘要"，用成本换质量——这是预算与精度的 trade-off，答出这个权衡比背 200 这个数字更重要。

**Q2：为什么问句不截断、回答截断？**
答：问句平均几十字，截断省不了多少却可能砍掉关键约束（"不要推荐辣的"砍成"不要推"）；回答动辄上千字，是大头。砍预算要砍大头，这是"花最小代价省最多 token"的选择。

**Q3：4000 token 超了之后为什么不直接丢最旧的？**
答：那是"丢信息"；合并压缩是"压信息"——5 条摘要合成 1 条，语义还在只是更粗。丢弃是最后手段，压缩优先。而且压缩只压长期部分，短期 3 轮原文是"对话连贯性"的命根子，不动。

**Q4：这套双压缩的边界在哪（什么场景会失效）？**
答：① 用户一轮说了很多偏好细节，一句话摘要装不下——靠冲突取代（相似度 ≥0.90 新旧替换）和多主题分条缓解；② 短期窗口 3 轮外的追问（"回到我们第 5 轮说的那个方案"）——短期已滚出窗口，只能靠长期摘要兜底，细节必丢；③ 这是容量问题的固有取舍，面试时主动说出失效场景比只说优点更加分。

**Q5：为什么说"提前压缩近期对话"是坑？**
答：代词依赖原文。"用户问：那它呢"被压成"主题：烤鸭价格"，下一轮模型看到的是孤立的"主题：烤鸭价格"，既不知道这是追问，也不知道和上一句的关系。指代消解（coreference）必须见到原文字面——这是语言学的硬约束，不是工程偏好。

## 七、简单总结

1. 双策略的本质：**长期"存时压"（摘要入库，用零成本）+ 短期"用时压"（原文入库，[:200] 截断）**，因为近期细节还有用、久远细节没价值
2. 三个数字：AI 回答截 **200 字符**（memory_manager.py:415）、短期窗口 **3 轮**（config.py:118）、溢出阈值 **4000 token**（config.py:113）触发合并压缩（memory_manager.py:201-205）
3. 最容易踩的坑：对近期对话也提前摘要——代词（"它""那个"）脱离原文就是废信息，追问链直接断掉
