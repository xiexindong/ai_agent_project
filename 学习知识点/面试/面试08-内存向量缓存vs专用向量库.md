# 面试08：工具/技能向量为什么不进 Milvus，自己算余弦？

> 配套代码：`modules/tools/tool_rag.py:63-71`（内存三张表）、`modules/tools/tool_rag.py:210-263`（_recall_vector 自己算余弦）、`modules/tools/tool_rag.py:364-373`（手写 _cosine）、`modules/skills/skill_registry.py:109`（`_vec_cache`）、`modules/rag/vector_store.py:120-176`（对照组：Milvus 建集合/建索引/load）
> 一句话结论：**量级决定选型——工具和技能只有几个到几十个，字典遍历余弦是微秒级、零依赖；Milvus 的价值从"万级向量"才开始，为几个工具引入一个常驻数据库服务是负收益。**

## 零、先扫盲：本文会用到的术语（大白话版）

| 术语 | 大白话解释 |
|---|---|
| 向量 | 一串数字（本项目 1024 个），是一句话/一个工具的"语义坐标" |
| 余弦相似度 | 比较两个语义坐标的方向有多一致。就像查通讯录：50 个联系人用眼睛扫一遍就行，50 万个才需要搜索引擎 |
| 进程内存 dict | 程序自己脑子里的一个 Python 字典，读写是纳秒~微秒级，但进程一重启就没 |
| Milvus | 专用的向量数据库：独立部署的服务，带 ANN 索引（近似最近邻），擅长在百万级向量里毫秒级找人 |
| ANN 索引 | "近似最近邻"索引：不保证找到绝对最像的，但保证"几乎最像"且极快。像查字典的偏旁部首索引——先定位到几个桶，再在桶里细查 |
| pgvector | PostgreSQL 的向量插件，让普通业务表也能存向量、用 SQL 算相似度，不用额外部署服务 |
| 懒加载 | 用到才算、算完缓存。技能向量第一次参与比对时才调 embedding，之后复用 |

## 一、先说结论

| 面试问 | 一句话答 |
|---|---|
| 为什么自己算？ | 向量总量 < 100 条，全量算余弦 O(N) 也就几十次乘加，微秒级 |
| 为什么不进 Milvus？ | 省下的计算 < 引入的成本（部署、连接、索引构建、故障面） |
| 存哪？ | 进程内存字典：`tool_rag._vectors`（tool_rag.py:68）、`skill_registry._vec_cache`（skill_registry.py:109） |
| 什么时候必须换 Milvus？ | 向量数万级以上、或需要持久化/多进程共享/复杂过滤时 |
| Milvus 在本项目管什么？ | **RAG 知识库**（Milvus），与**记忆注入**（PG+pgvector）是 prompt 里并列的两栏，不能混称 |

## 二、大白话拆解：同一个项目里的三种向量方案

| | Tool-RAG / 技能路由 | 记忆（长期召回） | RAG（知识库） |
|---|---|---|---|
| 存储 | 进程内存 dict | PG 表 + pgvector 列 | Milvus 集合 |
| 检索 | 手写余弦全量算 | SQL `<=>` 算子 + ivfflat 索引 | ANN 索引（IVF_FLAT, COSINE） |
| 向量量级 | 几个~几十个 | 每用户几百~几千条 | 万级~百万级 chunk |
| 数据归属 | 代码里定义的静态清单 | 用户产生的动态数据 | 文档切分的产品数据 |
| 生命周期 | 随进程 | 随用户（90 天归档） | 随文档版本 |

手写余弦，不引 numpy（tool_rag.py:364-373）：

```python
def _cosine(a: List[float], b: List[float]) -> float:
    if not a or not b or len(a) != len(b):
        return 0.0
    dot = sum(x * y for x, y in zip(a, b))   # 点积
    na = sum(x * x for x in a) ** 0.5        # a 的模
    nb = sum(y * y for y in b) ** 0.5        # b 的模
    if na == 0 or nb == 0:
        return 0.0
    return dot / (na * nb)                   # 点积 / (模×模)
```

## 三、输入 → 处理 → 输出对照

```python
# Tool-RAG 召回（参数默认值见 tool_rag.py:63-65）
ToolRAGIndex(top_k=5, min_score=0.25)
recall("今天北京天气怎么样")
# 内部过程: query 向量 × 每个工具向量，逐个算余弦 → 排序 → 0.25 过滤 → 截前 5
# 输出: [ToolHit("weather", 0.7412, "vector"), ToolHit("web_search", 0.5231, "vector")]
#        （若还有个 0.19 的无关工具，低于 0.25 被过滤掉）

# 量级对比（为什么够用）：
#   10 个工具 × 1024 维 = 10 次点积 ≈ 万次浮点乘加 → 亚毫秒
#   10 万个 chunk × 1024 维 = 1 亿次浮点乘加 → 秒级，必须 ANN 索引（Milvus 的主场）
```

三种方案的调用链路对比：

```
内存方案（工具/技能）          PG+pgvector（记忆）            Milvus（知识库）
─────────────────           ─────────────────            ─────────────────
query → embed 一次           query → embed 一次            query → embed 一次
  ↓                            ↓                             ↓
遍历 dict 算余弦（µs级）      一条 SQL（<=> 排序）           连服务 → ANN 检索
  ↓                            ↓                             ↓
排序 → 过滤 → 截断            fetchall 返回                 合并多集合 → 阈值过滤
零外部依赖                     依赖 PG（本来就有）            依赖独立 Milvus 服务
```

## 四、关键设计对照表：为什么是这么写

| 做法 | 原因（不这么写会怎样） |
|---|---|
| 向量存进程内存 dict | 进 Milvus：多一个常驻服务要部署、要探活、要建索引；工具清单是代码定义的静态数据，进程重启跟着代码重建，天然一致 |
| embedding 结果缓存（`_vec_cache` 懒加载） | 不缓存：每次路由都调一次 embedding API，白花钱加几百 ms 延迟 |
| 余弦手写（tool_rag.py:364） | 引 numpy/scipy 为 10 个向量算余弦：依赖与启动开销远超收益 |
| 工具画像变化时重新编码（tool_rag.py:105-109）/ 技能重名注册时清缓存（skill_registry.py:128） | 不清：路由永远用旧向量，改了工具描述/技能文案模型却按旧画像召回 |
| RAG 走 Milvus 不走内存 | 知识库 chunk 万级起步，全量算余弦秒级延迟；Milvus 的 ANN 索引把它压到毫秒 |
| 记忆走 PG+pgvector 不走 Milvus | 记忆要跟会话/用户数据一起事务管理（归档、删除、user_id 过滤），PG 一条 SQL 全办了；拆到 Milvus 要维护双库一致性 |

## 五、量级分界线（面试可直接背）

| 向量数 | 推荐方案 | 理由 |
|---|---|---|
| < 100 | 内存 dict + 全量余弦 | O(N) 就是几十次乘加，任何外部依赖都是负收益 |
| 1 千 ~ 10 万 | PG + pgvector（ivfflat 索引） | 与业务数据同库，事务一致，SQL `<=>` 算子够快 |
| > 10 万 / 多集合 / 复杂过滤 | Milvus 等专用向量库 | ANN 索引 + 分布式 + 标量过滤才是它的主场 |

本项目恰好三种量级各得其所：工具/技能（个位数，内存）、记忆（千级，PG）、知识库（万级，Milvus）。

## 六、面试追问（附回答要点）

**Q1：内存方案重启就丢，不怕吗？**
要点：不怕，因为索引内容是**代码定义的静态数据的派生物**——工具清单在代码里，重启后按代码重建索引，天然与代码版本一致。丢的不是"数据"是"缓存"。真正怕丢的是用户产生的记忆，所以它放 PG。

**Q2：多进程部署时内存 dict 会不会不一致？**
要点：会各存一份，但内容一致——输入都是同一份代码里的工具清单，embedding 模型也是同一个，各进程算出的向量相同。真正需要共享存储的场景是"运行期动态写入"（如用户记忆），那种场景本来就没选内存方案。

**Q3：工具数量涨到 500 个怎么办？**
要点：500 × 1024 维全量余弦约 50 万次乘加，仍是毫秒级，内存方案还能扛；但要开始关注两点：① embedding 缓存的内存占用（500 条约 2MB，无碍）；② 若工具变成"运行期动态注册/多实例共享"，就该迁到 PG+pgvector。迁移的分界线是**量级和共享需求**，不是某个神奇数字。

**Q4：Milvus 在本项目里除了存储还提供了什么，是内存方案给不了的？**
要点：三样。① ANN 索引：万级以上毫秒召回（IVF_FLAT 分桶，nprobe=16 扫 128 桶中的 16 个，vector_store.py:496）。② 标量过滤：检索时带 `kb_code in [...]` 权限表达式（vector_store.py:341-342）。③ 持久化与多集合管理：整库 drop、按文档下线、按库统计（vector_store.py:214、514、540）。

**Q5：记忆为什么不用 Milvus，用 PG+pgvector？**
要点：记忆不是纯检索问题，是**业务数据管理问题**——要按 user_id 隔离、要随会话归档删除、要置 superseded 状态、要和对话行同事务。这些在 PG 里是一条 SQL 的事；放 Milvus 就得维护"向量库 + 业务库"双写一致性，故障面翻倍。pgvector 的 ivfflat 索引对千级数据绰绰有余。

## 七、简单总结

1. 选型看**量级**不看技术时髦度：工具/技能几个向量 → 内存 dict 手写余弦（tool_rag.py:364）；记忆千级 → PG pgvector；知识库万级 → Milvus
2. 三个数字：Tool-RAG **top_k=5、min_score=0.25**（tool_rag.py:63-65）；向量缓存懒加载一次后复用
3. 术语红线：**记忆注入（PG+pgvector）≠ RAG（Milvus）**，两者在 prompt 里是并列两栏（`## 知识库参考` 与 `## 历史记忆`），面试混称直接扣分
