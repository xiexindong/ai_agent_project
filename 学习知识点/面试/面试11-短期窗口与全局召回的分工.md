# 面试11：为什么不把全部历史塞上下文，也不全走向量检索？

> 配套代码：`modules/memory/memory_manager.py:159-212`（build_context）、`modules/prompt/builtin.py:83-89`（prompt 分栏）、`config.py:118、121`
> 一句话结论：**短期窗口管"精准"（最近 3 轮原文逐字进 prompt，撑住追问），长期召回管"覆盖"（全历史语义 top-5 摘要，跨会话记得偏好）；全塞上下文会被 token 上限和噪声拖死，全走向量会把"刚才那句话"也压成摘要、追问直接断线——两套机制各治一头，缺一不可。**

---

## 一、先说结论

| 面试问 | 一句话答 |
|---|---|
| 为什么不全塞上下文？ | token 窗口有限（记忆栏预算 4000），且 20 轮前的全文对当前问题是噪声 |
| 为什么不全走向量？ | 向量召回给的是"摘要"不是原文；"那它呢？"这种追问必须逐字原文在场 |
| 两套怎么分工？ | 短期：当前会话最近 3 轮**原文**；长期：全部历史语义召回 **top-5 摘要** |
| 在 prompt 哪一栏？ | `## 历史记忆`（memory_context）——与 `## 知识库参考`（RAG）并列两栏，职责不同 |

---

## 二、大白话拆解：build_context 的两条取数管道

```python
# memory_manager.py:159 build_context
long_term = self._recall_long_term(query, user_id, query_embedding)
#   └─ PG pgvector 语义召回 top_k=5，阈值 0.65 过滤，关键词 2-gram 二次校验
#      范围：该用户【全部会话】的摘要向量 —— 跨会话

short_term = self.pg.get_short_term_history(session_id, user_id, self._short_rounds)
#   └─ SQL: WHERE session_id=%s AND user_id=%s ORDER BY created_at DESC LIMIT 3
#      范围：仅【当前会话】最近 3 轮原文 —— 不做任何语义计算

context_text = self._format_context(long_term, short_term, query)
#   └─ 拼成【历史记忆摘要】+【近期对话】两块（见面试10）
```

| 部分 | 大白话解释 |
|---|---|
| `_recall_long_term` | 全局搜：跨所有会话找语义相近的历史摘要（"很久以前聊过类似的吗"） |
| `get_short_term_history` | 翻最近几页：只看当前会话最近 3 轮，原文照搬（"刚才咱聊到哪了"） |
| `top_k=5` + `0.65` | 长期召回宁缺毋滥：语义不像的历史不进 prompt |
| `LIMIT 3` | 短期窗口固定 3 轮：再多就挤占预算，且 3 轮外的细节靠长期召回补 |

## 三、输入 → 输出对照

```python
# 场景：用户三个月前说过"我是做财务的"，本轮刚问过"差旅标准"，现在追问"那高铁票呢"
build_context(session_id="s9", user_id="cli-user", query="那高铁票呢")

# 短期管道（SQL LIMIT 3，原文）:
short_term = [
    {"query": "差旅标准是多少", "answer": "机票经济舱、住宿每晚350..."},
    {"query": "报销要什么材料", "answer": "发票、行程单..."},
]

# 长期管道（语义召回，摘要；本轮问句和"财务偏好"语义并不近，但查差旅时召回了）:
long_term = [
    {"summary": "用户是财务岗，报销类问题需给合规口径", "similarity": 0.71},
]

# context_text 渲染后:
# 【历史记忆摘要】
# - 用户是财务岗，报销类问题需给合规口径
#
# 【近期对话】
# 用户: 差旅标准是多少
# AI: 机票经济舱、住宿每晚350...
# 用户: 报销要什么材料
# AI: 发票、行程单...
#
# 模型拿到：追问的"上文"（短期原文）+ 用户的长期画像（长期摘要）
```

```
反例对照——只用其中一套：
  只长期（全向量）: "那高铁票呢"检索到的是摘要"差旅标准咨询"，
                    "高铁票"三个字不在摘要里 → 追问落空
  只短期（全上下文）: 三个月前的"我是做财务的"早滚出 3 轮窗口 → 画像丢失
```

## 四、为什么要这么写

| 做法 | 原因（不这么写会怎样） |
|---|---|
| 短期固定 3 轮不走向量 | 3 轮内是"对话连贯性"问题，语义检索解决不了指代（"它""那个"必须原文在场） |
| 长期只给摘要 top-5 | 全历史塞 prompt：几十轮后必爆 token；且旧对话全文对当前问题 95% 是噪声 |
| 长期召回前有 0.65 阈值 + 关键词二次校验 | 不过滤：问数学题召回到"天气"记忆，上下文被污染，回答质量下滑 |
| 短期查询双条件（session_id + user_id） | 只按 session 查：会话串号时把别人的对话拼进来 |
| 记忆栏与 RAG 栏并列而非合并 | 两栏数据源不同（PG vs Milvus）、时效不同、过滤逻辑不同（user_id vs kb_code 权限），混拼后没法独立裁剪（PromptBuilder 按栏优先级裁剪） |

---

## 五、简单总结

1. 分工本质：**短期窗口保"逐字精准"（3 轮原文，追问靠它），长期召回保"跨会话覆盖"（top-5 摘要，画像靠它）**，两套机制互补不替代
2. 四个数字：短期 **3 轮**（config.py:118）、长期 **top-5**、阈值 **0.65**、记忆栏 token 预算 **4000**（超了触发合并压缩）
3. prompt 里 `## 历史记忆`（记忆注入，PG+pgvector）与 `## 知识库参考`（RAG，Milvus）是**并列两栏**——数据源、权限、时效逻辑全不同，面试不能混称
