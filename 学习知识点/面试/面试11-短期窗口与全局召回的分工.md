# 面试11：为什么不把全部历史塞上下文，也不全走向量检索？

> 配套代码：`modules/memory/memory_manager.py:159-213`（build_context）、`memory_manager.py:218-326`（_recall_long_term）、`modules/memory/pg_manager.py:654-707`（get_short_term_history）、`modules/prompt/builtin.py:85-89`（prompt 分栏）、`config.py:118、121`
> 一句话结论：**短期窗口管"精准"（最近 3 轮原文逐字进 prompt，撑住追问），长期召回管"覆盖"（全历史语义 top-5 摘要，跨会话记得偏好）；全塞上下文会被 token 上限和噪声拖死，全走向量会把"刚才那句话"也压成摘要、追问直接断线——两套机制各治一头，缺一不可。**

---

## 〇、名词先扫盲（大白话版）

| 术语 | 大白话解释 |
|---|---|
| **短期窗口** | "刚才咱聊到哪了"——当前会话最近 3 页聊天记录，原样照搬。像翻手边的便签 |
| **长期召回（向量检索）** | "很久以前聊过类似的吗"——把当前问句变成一个"语义坐标"（向量），在全部历史摘要里找坐标最近的 5 条。像图书馆按主题找书，而不是按书名逐字找 |
| **向量 / embedding** | 把一句话变成一串数字（本项目 1024 维），语义相近的话数字也相近。"报销流程"和"差旅审批"措辞不同但坐标很近 |
| **相似度阈值 0.65** | 及格线：语义分低于 0.65 的历史直接丢掉，宁缺毋滥 |
| **top-k** | 只取最相近的前 k 条（本项目 k=5），不是全捞 |
| **关键词二次校验** | 向量说"语义像"之后再问一句"字面有没有共同词块"——双保险，防"语义近但完全无关"的误匹配 |
| **prompt 分栏** | 喂给模型的提示词按"## 知识库参考""## 历史记忆"等标题分块，各块数据独立裁剪 |

## 一、先说结论

| 面试问 | 一句话答 |
|---|---|
| 为什么不全塞上下文？ | token 窗口有限（记忆栏预算 4000，config.py:113），且 20 轮前的全文对当前问题是噪声 |

| 在 prompt 哪一栏？ | `## 历史记忆`（memory_context，builtin.py:86）——与 `## 知识库参考`（RAG，builtin.py:85）并列两栏，职责不同 |

## 二、大白话拆解：build_context 的两条取数管道

```
build_context(session_id, user_id, query)          memory_manager.py:159
   │
   ├─ 管道① 长期召回  _recall_long_term(query, user_id, query_embedding)   :218
   │     ├─ query 没给向量就先 embed 一次（:246-247）
   │     ├─ pg.search_memory_by_vector 取 top_k=5（:251-253，跨该用户全部会话）
   │     ├─ 相似度 ≥ 0.65 过滤（:254-257）
   │     ├─ 关键词 2-gram 二次校验（:281-296；全部不中不清空，标低置信交人工）
   │     └─ 时效衰减重排：有效分 = similarity × 0.5^(天数/180)（:311-324）
   │
   ├─ 管道② 短期窗口  pg.get_short_term_history(session_id, user_id, 3)   :194
   │     └─ SQL: WHERE session_id=%s AND user_id=%s
   │             ORDER BY created_at DESC LIMIT 3   （pg_manager.py:695-701）
   │             再 reverse 翻回旧→新自然语序（pg_manager.py:703）
   │        范围：仅【当前会话】最近 3 轮原文 —— 不做任何语义计算
   │
   ├─ _format_context 拼成【历史记忆摘要】+【近期对话】两块（:198，细节见面试10）
   │
   └─ 超 4000 token？→ _compress_long_term 合并长期摘要重拼（:201-205）
   ↓
返回 dict: {long_term_memory, short_term_memory, context_text,
            compressed, low_confidence}              （:207-213）
```

核心代码片段（modules/memory/memory_manager.py:192-198）：

```python
# memory_manager.py:192-198 —— 两条管道各取各的，互不干扰
long_term = self._recall_long_term(query, user_id, query_embedding)

short_term = self.pg.get_short_term_history(
    session_id, user_id, self._short_rounds
)

context_text = self._format_context(long_term, short_term, query)
```

| 部分 | 大白话解释 |
|---|---|
| `_recall_long_term` | 全局搜：跨所有会话找语义相近的历史摘要（"很久以前聊过类似的吗"） |
| `get_short_term_history` | 翻最近几页：只看当前会话最近 3 轮，原文照搬（"刚才咱聊到哪了"） |
| `top_k=5` + `0.65` | 长期召回宁缺毋滥：语义不像的历史不进 prompt |
| `LIMIT 3` | 短期窗口固定 3 轮：再多就挤占预算，且 3 轮外的细节靠长期召回补 |
| `WHERE session_id AND user_id` | 双条件：只按 session 查，会话串号时会把别人的对话拼进来 |
| 时效衰减重排 | "又新又像"的排前面：180 天前的记忆权重减半，360 天剩 1/4 |

**时效衰减的计算例子**（memory_manager.py:314-321）：

```
两条记忆语义分同为 0.91：
  今天写的      天数=0    → 有效分 0.91 × 1.00 = 0.910   ← 排前面
  180 天前的    天数=180  → 有效分 0.91 × 0.50 = 0.455
  360 天前的    天数=360  → 有效分 0.91 × 0.25 = 0.228
注意：衰减只影响排序顺序，不写回 similarity 字段——
     否则刚过 0.65 阈值的记忆会被误判成"低置信"
```

## 四、关键设计对照表

| 维度 | 短期窗口 | 长期召回 |
|---|---|---|
| 范围 | 仅当前会话 | 该用户全部会话 |
| 内容形态 | 原文（回答截 200 字） | 一句话摘要 |
| 取数方式 | SQL 按时间 LIMIT 3 | 向量余弦距离 top-5 |
| 有无语义计算 | 无（纯按时间） | 有（embed + 相似度 + 关键词校验 + 时效衰减） |
| 解决的问题 | 对话连贯（指代、追问） | 跨会话覆盖（偏好、画像） |
| 失效场景 | 3 轮外的细节必滚出 | 追问类短句语义弱，召不准 |

---

## 五、为什么要这么写

| 做法 | 原因（不这么写会怎样） |
|---|---|
| 短期固定 3 轮不走向量 | 3 轮内是"对话连贯性"问题，语义检索解决不了指代（"它""那个"必须原文在场） |
| 长期只给摘要 top-5 | 全历史塞 prompt：几十轮后必爆 token；且旧对话全文对当前问题 95% 是噪声 |
| 长期召回前有 0.65 阈值 + 关键词二次校验 | 不过滤：问数学题召回到"天气"记忆，上下文被污染，回答质量下滑 |
| 短期查询双条件（session_id + user_id） | 只按 session 查：会话串号时把别人的对话拼进来 |
| 关键词校验全不中时不清空、标低置信 | 相似度明明过了 0.65，可能只是措辞差异；清空太武断——保留结果 + 置 `_low_confidence=True`，交上层触发人工审核（memory_manager.py:294-296） |
| 记忆栏与 RAG 栏并列而非合并 | 两栏数据源不同（PG vs Milvus）、时效不同、过滤逻辑不同（user_id vs kb_code 权限），混拼后没法独立裁剪（PromptBuilder 按栏优先级裁剪） |

## 六、可能的追问与回答要点

**Q1：短期窗口为什么是 3 轮不是 10 轮？**
答：token 预算与收益的权衡。3 轮 ×（问句 + 200 字回答）≈ 600 字，占记忆栏预算小头；拉到 10 轮翻三倍，挤占 RAG 栏和工具观察的预算。且实测多轮追问的指代链 rarely 超过 3 跳——超过的部分由长期摘要兜底（虽然粗但有）。数字可调（config.py:118 是配置项），调的是权衡不是对错。

**Q2：向量召回为什么比关键词检索（如 ES）更适合长期记忆？**
答：用户三个月后不会用原词。上次说"我在财务部上班"，这次问"差旅标准"——关键词零重合，但语义坐标很近。向量检索抓的是"意思像"而不是"字面同"，这正是跨会话记忆需要的。但纯语义会误匹配（"报销流程"召回"差旅审批"），所以再加一道关键词 2-gram 校验，两种信号互补。

**Q3：两条管道的结果会不会重复/打架？**
答：会重复（当前会话最近一轮刚入库，长期召回可能又把它捞回来），但不打架：① 重复信息只是多花一点 token，不会让模型困惑；② 真想抠掉可以在长期召回里排除当前 session_id，本项目没做——属于"成本大于收益"的省略；③ 打架（新旧记忆矛盾）由入库时的冲突取代解决（相似度 ≥0.90 旧的置 superseded），不是召回阶段的事。

**Q4：低置信（low_confidence）标记之后发生了什么？**
答：标记写进返回 dict（memory_manager.py:212），save 节点的自动初审会检查它：命中即把本轮挂进人工复核队列（graph.py:323-324，review 类型 low_sim）。设计哲学是"拿不准就不装懂，但也别打断用户"——本轮照常回答，事后人工看。

**Q5：如果让你优化这套分工，你会动哪里？**
答：① 短期窗口从"固定 3 轮"改成"按 token 动态伸缩"（问答短就多带几轮）；② 长期召回排除当前会话已进短期窗口的条目，去重；③ 追问检测：识别出"那它呢"类追问时跳过长期召回（短句向量质量差），省一次 embed；④ 答出任意一条 + 说出权衡即可，重点是展示你理解两套机制各自的失效边界。

## 七、简单总结

1. 分工本质：**短期窗口保"逐字精准"（3 轮原文，追问靠它），长期召回保"跨会话覆盖"（top-5 摘要，画像靠它）**，两套机制互补不替代
2. 四个数字：短期 **3 轮**（config.py:118）、长期 **top-5**（memory_manager.py:252）、阈值 **0.65**（config.py:121）、记忆栏 token 预算 **4000**（config.py:113，超了触发合并压缩）
3. prompt 里 `## 历史记忆`（记忆注入，PG+pgvector，builtin.py:86）与 `## 知识库参考`（RAG，Milvus，builtin.py:85）是**并列两栏**——数据源、权限、时效逻辑全不同，面试不能混称
