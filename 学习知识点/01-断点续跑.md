# 01 断点续跑：项目中如何实现

## 一、实现链路

```
graph.py:271   _graph.invoke(initial_state)         图开始跑
    ↓
graph.py:217   update_session_state(session_id, agent_state.to_dict())   ← 唯一存档点
    ↓
pg_manager.py:400  update_session_state(session_id, agent_state)

    ↓

```

涉及的 4 个文件：

| 文件 | 位置 | 职责 |
|---|---|---|
| `modules/agent/state.py` | 全文 | 定义状态结构 `AgentState` / `AgentStateDict` |
| `modules/agent/graph.py` | `214-219` | save 节点调用存档 |
| `modules/memory/pg_manager.py` | `399-430` | 存档（写 DB） |
| `modules/memory/pg_manager.py` | `432-459` | 读档（读 DB） |

## 二、链路逐段解析

### 1. 表结构（`init_db.sql:19`）

```sql
agent_state  JSONB DEFAULT '{}'::jsonb   -- Agent任务状态、待办、已完成任务、关键结果
```

一行会话 = 一个 `agent_state`，存在**会话主表** `chat_session` 上，不是 `chat_history`。
新建会话时是 `{}`（`create_session` 只插 `session_id/user_id/title`，不传 `agent_state`）。

### 2. 存档调用（`graph.py:214-219`）

```python
from modules.agent.state import AgentState
agent_state = AgentState.from_dict(state)          # dict → dataclass
self.agent.memory.pg.update_session_state(
    session_id, agent_state.to_dict()              # dataclass → dict
)
```

为什么转来转去：LangGraph 节点之间只传 `dict`，业务代码用 `dataclass` 点属性更方便，所以 `from_dict` / `to_dict` 成对出现（见 `state.py:101` / `state.py:146`）。

⚠ **整段覆盖，不是合并** —— `to_dict()` 返回全量 30 个字段，SQL 是 `SET agent_state = %s`，旧值被整个替换。

### 3. 存档函数（`pg_manager.py:400`）

```python
@handle_exception(default=None, log_msg="更新会话状态异常", reraise=True)
def update_session_state(self, session_id: str, agent_state: dict) -> None:
```

| 参数 | 类型 | 说明 |
|---|---|---|
| `session_id` | `str` | 定位哪一行（`WHERE` 条件） |
| `agent_state` | `dict` | 要存的全量状态，内部 `json.dumps` 后写入 |
| 返回值 | `None` | 只写不读 |

装饰器参数：`reraise=True` → 存失败**直接抛异常**，不静默吞掉（关键写路径）。
⚠ 因此 `default=None` 实际不生效（两条 except 都先 raise）。

### 4. 写入 SQL（`pg_manager.py:426`）

```sql
UPDATE chat_session
SET agent_state = %s, updated_at = CURRENT_TIMESTAMP
WHERE session_id = %s
```

| 占位符 | 值 |
|---|---|
| 第 1 个 `%s` | `json.dumps(agent_state, ensure_ascii=False)` |
| 第 2 个 `%s` | `session_id` |

`ensure_ascii=False` → 中文不被转义成 `\u4f60`。
`updated_at = CURRENT_TIMESTAMP` → 由数据库取时间，避免应用服务器时区不一致。

### 5. 读档函数（`pg_manager.py:433`）

```python
@handle_exception(default={}, log_msg="读取会话状态异常")
def get_session_state(self, session_id: str, user_id: str) -> dict:
```

| 参数 | 说明 |
|---|---|
| `session_id` | 查哪一行 |
| `user_id` | **安全隔离** —— `WHERE session_id=%s AND user_id=%s`，防止 A 读 B 的状态 |
| 返回值 | `dict`，查不到返回 `{}` |

注意这里**没有 `reraise`**（默认 `False`）→ 读失败**返回 `{}` 降级**，不抛异常。

```python
row = self._cur.fetchone()
return row[0] if row and row[0] else {}
```

`row` 为 `None`（没这条记录）或 `row[0]` 为 `{}`（空状态）都兜底成 `{}`。

## 三、存了什么：`agent_state` 字段全解析

来源 `state.py:12-61`（`AgentStateDict`），共 30 个字段，按用途分 9 组：

### ① 会话信息（3）

| 字段 | 类型 | 说明 |
|---|---|---|
| `session_id` | str | 会话 ID |
| `user_id` | str | 用户 ID |
| `user_query` | str | **本轮**用户问的原话 |

### ② 消息历史（1）

| 字段 | 类型 | 说明 |
|---|---|---|
| `messages` | list | 兼容 LangGraph `MessagesState` 的消息列表 |

### ③ RAG 知识库（2）

| 字段 | 类型 | 说明 |
|---|---|---|
| `rag_context` | str | 召回后拼好的知识库文本（注入 Prompt 用） |
| `rag_sources` | list | 召回来源（文件名 + 分数），落库时写入 `chat_history.rag_sources` |

### ④ Skill 技能（2）

| 字段 | 类型 | 说明 |
|---|---|---|
| `active_skill` | str | 命中的技能名，未命中为空串 |
| `skill_context` | str | 注入推理 Prompt 的技能 SOP 文本 |

### ⑤ 记忆上下文（5）

| 字段 | 类型 | 说明 |
|---|---|---|
| `memory_context` | str | 长+短期记忆拼好后的文本 |
| `long_term_memory` | list | 向量召回的长期记忆 |
| `short_term_memory` | list | 最近 N 轮短期记忆 |
| `memory_compressed` | bool | 记忆是否已压缩（防重复压缩） |

### ⑥ ReAct 循环（7）—— 续跑的核心

| 字段 | 类型 | 说明 |
|---|---|---|
| `iteration` | int | **当前第几轮**（`max_iterations` 上限内） |
| `max_iterations` | int | 最大轮次，默认 10 |
| `reasoning` | str | Reason：本轮 LLM 的思考 |
| `action` | dict | Action：要调的工具 `{name, arguments}` |
| `observation` | str | Observation：工具返回的结果 |
| `tool_call_logs` | list | 全量工具调用日志（落库用） |
| `tool_calls_history` | list | 工具调用历史（去重/防死循环用） |

### ⑦ 任务编排（3）

| 字段 | 类型 | 说明 |
|---|---|---|
| `sub_tasks` | list | 拆解出的子任务队列 |
| `current_task_index` | int | 当前做到第几个子任务 |
| `task_results` | list | 已完成子任务的结果 |

### ⑧ 最终输出（3）

| 字段 | 类型 | 说明 |
|---|---|---|
| `final_answer` | str | 完整详细答案 |
| `llm_summary` | str | 一句话摘要 |
| `summary_embedding` | list | 摘要向量（1024 维） |

### ⑨ 控制位（3）—— 决定图怎么走

| 字段 | 类型 | 说明 |
|---|---|---|
| `need_tool_call` | bool | 是否要调工具 |
| `finished` | bool | 是否已完成 |
| `error` | str | 错误信息 |

> `need_tool_call` / `finished` / `error` 三个是 `_should_continue`（`graph.py:225`）的判据：
> `finished=True` → answer；`need_tool_call=True and not error` → act；其余 → answer。

## 四、现状：只做了「存」，没做「读回续跑」

证据 1 —— 入口每次都是全新状态（`graph.py:265`）：

```python
initial_state = {
    "session_id": session_id,
    "user_id": user_id,
    "user_query": query,
    "prepared": False,
}
```

只有 4 个字段，没有 `iteration`、没有 `tool_call_logs`，**从不调用 `get_session_state` 回填**。

证据 2 —— `get_session_state` 的 2 个调用点都不是续跑：

| 调用点 | 实际用途 |
|---|---|
| `server.py:225` | 越权校验，查不到 → 403 |
| `auth.py:72` | 权限判断 |

**结论**：当前 `agent_state` 的实际价值是**状态留痕 / 可观测**（能 SQL 查任意会话推理到第几轮、调了什么工具），不是断点续跑。

⚠ 别混淆：多轮对话连贯靠的是 `chat_history` 的历史问答 + 向量召回，与 `agent_state` 无关。

## 五、要真续跑，补 2 处

### 补 1：`run()` 读档（`graph.py:265`）

```python
saved = self.agent.memory.pg.get_session_state(session_id, user_id)
if saved and not saved.get("finished") and saved.get("user_query") == query:
    initial_state = {**saved, "prepared": True}      # 续跑：跳过 prepare
else:
    initial_state = {"session_id": session_id, "user_id": user_id,
                     "user_query": query, "prepared": False}
```

### 补 2：注意 `prepared` 字段

`_prepare_node` 靠 `state.get("prepared")` 判断是否要重新召回记忆（`graph.py:113`）。续跑时必须设 `True`，否则记忆会被重复召回一遍。

### 另外 3 个坑

| 坑 | 说明 |
|---|---|
| 状态过期 | 会话可能停在几天前，中间数据已变，拿旧观察结果作答会出错 |
| 向量字段太大 | `summary_embedding` 是 1024 维列表，转 JSON 存 JSONB 体积不小 |
| 官方方案更省事 | LangGraph 内置 `PostgresSaver` + `thread_id`，节点级自动存档/恢复，通常不必手写 |
