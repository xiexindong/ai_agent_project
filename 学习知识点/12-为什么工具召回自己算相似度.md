# 为什么工具召回自己算相似度，不用向量数据库？

> 配套代码：`modules/tools/tool_rag.py`（Tool-RAG 索引）
> 相关配置：`.env` 里的 `TOOL_RAG_ENABLED` / `TOOL_RAG_TOP_K` / `TOOL_RAG_MIN_SCORE`
> 一句话结论：**不是因为懒，也不是遗漏——在几十条工具的规模下，自己算反而更快、更准、更简单。**

---

## 一、先说结论

| 问题 | 答案 |
|---|---|
| 自己算的余弦准不准？ | **准，而且是精确解**。向量库算出来的反而是近似解 |
| 为什么不接 Milvus？ | 数据量太小（几十条），接了是过度设计，还多一个故障点 |
| 那持久化了吗？ | **向量没持久化，文本持久化了**（工具元数据落盘在 `data/mcp_catalog.json`） |
| 什么时候该换向量库？ | 工具数量上千、或多实例共享、或需要热更新时 |

---

## 二、一个比喻：找人要问多少个人？

假设你要在一堆人里找出「最会修空调的那个」：

**场景 A：屋里只有 50 个人**
你挨个问一遍就行。问完 50 个，你百分之百确定找到了最会的那个。耗时几分钟。

**场景 B：全城 100 万人**
挨个问不现实。你只能查「黄页索引」——按区域分成 128 个片区，只去最可能有答案的 16 个片区找。耗时很快，但万一最厉害那位住在你没去的片区，你就漏了。

向量数据库（Milvus）就是场景 B 的「黄页索引」。它存在的唯一理由是**数据量大到挨个算算不动了**，为此付出的代价是**允许漏召**。

而你的工具索引现在只有几十条，正处在场景 A。这时候上索引系统，等于给自己找麻烦。

## 三、代码里到底在干什么

### 3.1 建索引：算向量，存进内存字典

```python
# tool_rag.py:108  批量算向量（一次网络调用换 N 条向量）
vectors = get_embedding_service().embed_batch([t for _, t in pending])

# tool_rag.py:138-139  存进内存 dict，没有写任何数据库
for (name, _), vec in zip(pending, vectors):
    self._vectors[name] = vec
```

`_vectors` 的定义（68 行）就是普通字典：

```python
self._vectors: Dict[str, List[float]] = {}   # 工具名 → 语义向量
```

### 3.2 召回：遍历这个字典，逐个算余弦

```python
# tool_rag.py:189-192
scored = [
    ToolHit(name, round(_cosine(qv, vec), 4), "vector")
    for name, vec in self._vectors.items()      # 全量遍历，一个不落
]
scored.sort(key=lambda h: h.score, reverse=True)
hits = [h for h in scored if h.score >= self._min_score][:k]
```

### 3.3 余弦就是教科书公式

```python
# tool_rag.py:297-306
def _cosine(a, b):
    if not a or not b or len(a) != len(b):
        return 0.0
    dot = sum(x * y for x, y in zip(a, b))
    na = sum(x * x for x in a) ** 0.5
    nb = sum(y * y for y in b) ** 0.5
    if na == 0 or nb == 0:
        return 0.0
    return dot / (na * nb)
```

没有近似、没有采样、没有索引结构——就是 `dot / (|a|*|b|)`，把所有候选全算一遍，排序取前 k。

## 四、为什么不接向量数据库

### 4.1 规模根本没到

| 指标 | 你现在 | Milvus 的用武之地 |
|---|---|---|
| 工具条数 | 几十条（3 个 MCP 工具 + 若干本地工具） | 十万 ~ 百万 |
| 单次召回计算量 | 几十次内积 | 百万次内积 |
| 耗时 | 微秒级 | 秒级（若暴力算） |

一次余弦是 1024 次乘加（`EMBEDDING_DIMENSION=1024`）。50 条工具 = 5 万次浮点运算，现代 CPU 上零点几毫秒。这点开销淹没在「调 embedding 接口」的几十毫秒里，根本感知不到。

### 4.2 工具集合不需要持久化向量

这是最关键的设计判断：

|  | 知识库文档 | 工具画像 |
|---|---|---|
| 从哪来 | 用户上传，持续增加 | 代码 + 配置决定，启动时确定 |
| 丢了能重来吗 | 不能，文件没了就没了 | 能，重启重新算一遍即可 |
| 所以 | 必须持久化（进 Milvus） | 不需要（留内存） |

而且向量天然不适合长期存：它绑定了 embedding 模型和维度。哪天把智谱 `embedding-2` 换成别家模型，或把 `EMBEDDING_DIMENSION` 从 1024 改成 768，存下来的旧向量全部作废。

实际落盘的是文本而不是向量：`data/mcp_catalog.json` 里存的是工具元数据（名字/描述/参数），这些永远有效，向量每次启动现算。这个取舍是对的。

### 4.3 多接一个组件 = 多一个故障点

工具召回处在每一次对话的必经路径上：

```
原本：  query -> embed -> 本地算余弦 -> 结果
接入后：query -> embed -> 连 Milvus -> 网络往返 -> Milvus 检索 -> 结果
                          ^ 新增失败点：连不上 / 超时 / 集合未建 / 维度不匹配
```

Milvus 是项目里最重的依赖（`docker-compose.yml` 里为它单独起了 etcd + minio 两个支撑容器）。让它承担「几十条数据的检索」，等于把轻活交给重资产，还得为它做降级兜底。

现在的降级路径很干净：embedding 挂了 → 141-145 行捕获 → `_vector_available = False` → 改用关键词召回，服务照常可用。接了 Milvus 就得多一层「Milvus 挂了怎么办」。

### 4.4 省掉一整套运维负担

接向量库要额外处理：

- 集合创建、维度（1024）与模型版本对齐
- 工具增删改时的增量维护（删工具要去 Milvus 删一条）
- 多环境（本地 / Docker / 生产）的地址与连通性
- 集合 schema 迁移

内存方案只需要一件事：启动时 `index_tools()`。

## 五、自己算的准不准？

### 5.1 公式层面：完全一致

Milvus 那边声明的度量方式（`modules/rag/vector_store.py`）：

```python
137-141:  field_name="embedding",
          index_params={
              "index_type": "IVF_FLAT",
              "metric_type": "COSINE",      # 度量类型 = 余弦
              "params": {"nlist": 128},     # 数据被分成 128 个簇
          }

428:      param={"metric_type": "COSINE", "params": {"nprobe": 16}}   # 检索时只探 16 个簇
```

度量类型一模一样，都是 COSINE。所以「算一个相似度」这件事，两边没有任何区别。

### 5.2 检索层面：本地更准

|  | 本地暴力算 | Milvus IVF_FLAT |
|---|---|---|
| 覆盖范围 | 100%（每个都算） | nprobe/nlist = 16/128 ≈ 12.5% |
| 数学性质 | 精确解 | 近似解 |
| 会不会漏掉真正的第一名 | 不会 | 会（若它落在未探的簇里） |
| 数值精度 | Python float64 | 存储 float32（差异可忽略） |

本地算出的是「理论最优排名」的上界——任何近似算法的结果都不可能比它更准，只能逼近它。

结论很反直觉：**不是自己算凑合够用，而是自己算比向量库更准**。向量库牺牲精度换的是速度，不是提升精度。

### 5.3 还有一个 Milvus 的小坑

`nlist=128` 意味着数据被分成 128 个簇。如果数据只有几十条，绝大多数簇是空的，聚类质量很差，近似检索的准确率进一步下降。

数据量小于 nlist 时用 IVF 索引，属于明显的配置错配。

## 六、复杂度对比（专业视角）

| 维度 | 本地暴力 | Milvus IVF_FLAT |
|---|---|---|
| 建索引 | O(N) 次 embedding 调用 | 同 + 聚类训练 + 写入 |
| 单次检索 | O(N*d)，d=1024 | 约 O(N*d/8)（探 12.5%） |
| 空间 | O(N*d) 内存 | O(N*d) + 索引结构 + 服务内存 |
| 精度 | 精确 | 近似（召回率 < 100%） |
| 额外依赖 | 无 | 多个容器 + 网络连接 |

算一下真实开销：

```
N=50, d=1024
单次召回 = 50 x 1024 = 51,200 次乘加
         ≈ 0.05 ms（C 实现）/ 约 0.5 ms（Python 纯循环）

对比：一次 embedding 网络调用 ≈ 30~100 ms
结论：本地检索耗时不到网络调用的 1%
```

优化一个占比不到 1% 的环节，是典型的过早优化。

## 七、真正决定准不准的是什么

余弦算得再精确，召回质量也取决于这四件事（按影响从大到小）：

| 排序 | 因素 | 现状 | 怎么改 |
|---|---|---|---|
| 1 | 画像文本质量 | `tool_rag.py:254` 拼成「工具名。描述 可填参数: xxx」 | 描述含糊，向量就分不开。这是提升召回最有效的手段 |
| 2 | embedding 模型 | 智谱 `embedding-2`，1024 维 | 换更强的中文模型才有本质提升 |
| 3 | `min_score` 阈值 | 默认 0.25 | 太低放进无关工具污染 prompt；太高漏召。需按实测调 |
| 4 | 中英混排 | 查询中文、工具名英文 | 跨语言对齐天然弱一档，可在画像里补中文别名 |

这四条里没有一条跟「用不用向量库」有关。换成 Milvus 不会让召回更准，只会因为 nprobe 的近似性略微变差。

钱要花在刀刃上：把工具描述写清楚，比接一个 Milvus 有用得多。

## 八、什么时候必须换向量库

出现下面任一情况就该考虑：

| 信号 | 阈值 | 说明 |
|---|---|---|
| 工具数量暴涨 | N > 1000 | 启动编码变慢，单次召回 O(N*d) 开始有感知 |
| 多实例部署 | 3 个以上 worker | 每个进程各编码一份，浪费调用与内存 |
| 运行时热增减 | 工具动态注册 | 需跨进程共享索引，内存方案做不到 |
| 要求跨进程一致 | 严格 | 内存索引各进程独立，A 加的工具 B 看不到 |

### 真要换，改动点只有一处

`ToolRAGIndex._recall_vector()`（181-200 行）是唯一的检索出口，把它换成向量库检索即可，上层 `recall()` 和路由层完全不用动：

```python
# 现状：本地全量算余弦
scored = [ToolHit(name, round(_cosine(qv, vec), 4), "vector")
          for name, vec in self._vectors.items()]

# 改造后：换成 Milvus 检索（示意）
# hits = vector_store.search(collection="tool_index", query_vec=qv, limit=k)
```

这种「检索实现可替换」的结构，正是当初把检索收敛到一个方法里的价值——现在不用，将来要换只改一处。

## 九、常见误解 Q&A

**Q：没入库，重启岂不是要重算？**
是。代价是启动时一次 `embed_batch`（几十条，一条网络调用）。换来的是不用维护集合、不用担心维度/模型版本兼容。对几十条数据，这笔交易划算。

**Q：那 Milvus 在项目里干嘛用？**
存知识库文档切片（`knowledge_base` 集合）。那些是用户上传的、会持续增长的、丢了找不回来的，必须持久化。它跟工具索引是两套东西，别混为一谈。

**Q：日志里打了 Tool-RAG 索引已建立，是不是入库了？**
不是。`main.py:123` 打印的是内存索引的统计（工具条数等），跟 Milvus 没有任何关系。去 Milvus 查 `knowledge_base` 集合，里面不会有工具向量。

**Q：能不能把工具向量也塞进 Milvus 求个心安？**
可以但不建议。除了上面说的代价，还有个实际问题：`nlist=128` 而数据只有几十条，IVF 近似检索的准确率会比本地精确算更差。属于花钱买退步。

**Q：降级成关键词召回后还准吗？**
这是另一条路（`_recall_keyword`，204-217 行）：按 2-gram 片段重合打分，分数统一乘 `_KEYWORD_SCALE=0.6` 折算，弱证据不能盖过真实语义命中。比语义召回弱，但保证 embedding 挂了服务还能用。

## 十、一句话总结

1. **自己算的是精确解**：跟 Milvus 同一个余弦公式，但覆盖 100% 候选；Milvus 的 IVF_FLAT + nprobe=16 只探 12.5%，是近似解。
2. **向量库的价值是规模和速度，不是精度**。几十条工具的场景用不上这个交换，用了反而更差。
3. **不持久化向量是刻意取舍**：向量绑定模型和维度，容易作废；落盘的是文本（`data/mcp_catalog.json`），永远有效。
4. **真正的瓶颈在画像文本和 embedding 模型**，不在检索算法。
5. **换向量库的触发条件是规模**（N > 1000 或多实例共享），且只需改 `_recall_vector()` 一处。
