# 熔断是什么？（一篇搞懂）

> 对应代码：[llm.py#L221-L236](file:///e:/workspace/AI/AI-project/ai_agent_project/modules/agent/llm.py#L221-L236)
> 熔断器本体：[circuit_breaker.py](file:///e:/workspace/AI/AI-project/ai_agent_project/modules/common/circuit_breaker.py)

---

## 一句话比喻

**家里的电闸（保险丝）**：电路持续过载 → 电闸跳闸 → 你继续按开关也不会通电，先保护电器；等故障排除，再把闸合上，恢复供电。

熔断器就是给"主模型"装的电闸：**主模型连续失败 5 次 → 跳闸 → 后面 30 秒内试都不试它，直接换备用模型**。

跳闸期间省掉的，是"明明注定失败、却还要干等 30 秒超时"的那次请求。

---

## 为什么要这个？

没有熔断器时，主模型挂了，每个用户的每次提问都要经历：

```
请求主模型 → 等 30 秒超时 → 失败 → 换备用模型
                          ↑ 这 30 秒纯浪费，而且每个请求都浪费一遍
```

10 个并发用户 = 10 次白等。熔断器记住"它已经挂了"，**跨请求**拦截，不做无谓尝试。

---

## 三态状态机（核心就这张图）

```
        连续失败满 5 次
 ┌───────────────────────┐
 │                       ▼
CLOSED（正常）         OPEN（跳闸）
 放行、数失败次数        30 秒内一律拦掉，不调用
 ▲                       │
 │ 探针成功               │ 30 秒冷却到期
 │                       ▼
 └────────────────── HALF_OPEN（半开）
                       只放 1 个"探针"请求试试
                         │
                  探针成功 → CLOSED（恢复）
                  探针失败 → OPEN（重新冷却 30 秒）
```

**为什么半开只放 1 个请求？** 冷却 30 秒是定时器，不代表服务真的好了。一下把全部流量放过去，可能把刚缓过来的服务再次打挂。放一个探针：成功才恢复，失败立刻重新跳闸。

---

## 熔断 / 重试 / 降级：别搞混

| 机制 | 管什么 | 作用范围 | 生活比喻 |
|---|---|---|---|
| **重试** | 偶发抖动 | 一次请求内，同一下游再试几次 | 敲门没人应，再敲两下 |
| **熔断** | 持续故障 | **跨请求**，直接拦掉不调用 | 知道这家店关门了，不去了 |
| **降级** | 保住可用 | 被拦或失败后，换备用模型顶上 | 常去的店关了，换隔壁一家 |

顺序：**先问熔断器 `allow()` → 放行才真调 → 失败了走降级 → 失败累计够 5 次就跳闸**。

## JS 类比

相当于给 `fetch` 包一层，记住"这个接口最近一直挂"：

```js
// 熔断开关闭时：每次请求都先等它超时，30 秒白白浪费
async function chat(messages) {
  if (!breaker.allow('deepseek')) return fallbackChat(messages) // 跳闸中：直接换备用，不 fetch
  try {
    const r = await fetch('/deepseek', { body: messages })      // 正常调用
    breaker.recordSuccess('deepseek')                           // 报成功：计数清零
    return r
  } catch (e) {
    if (!isDegradable(e)) throw e                               // 400 参数错：换谁都没用，直接抛
    breaker.recordFailure('deepseek')                           // 报失败：计数 +1，满 5 次跳闸
    return fallbackChat(messages)                               // 换备用模型
  }
}
```

## 对照本项目代码走一遍（L221-236）

| 代码 | 在干什么 |
|---|---|
| `can_fallback and not breaker.allow(primary)` | 有备用模型 + 主模型正跳闸 → 进"直接降级"分支 |
| `self._request(fb, ...)` | 跳过主模型，直接请求备用模型（省 30 秒） |
| `self._request(primary, ...)` | 没跳闸，正常请求主模型 |
| `record_success(primary)` | 成功了：失败计数清零 |
| `if not _is_degradable(e): raise` | 400/401 这类请求本身的错 → 直接抛，**不降级也不记熔断** |
| `record_failure(primary)` | 超时/连接失败 → 记一次失败，满 5 次自动跳闸 |
| `self._request(fb, ...)` | 主模型真挂了 → 换备用模型再试一次 |

**一个关键细节**：熔断记录的只是"服务端故障"（超时、连接失败、429、5xx）。一次代码 bug 导致的参数错误不会被计入——否则主模型会被一次 bug 误跳闸，整条链路跟着受伤。

## 30 秒记住

1. 熔断 = 电闸：下游**持续**挂了就跳闸，跨请求快速失败，省超时等待。
2. 三态：CLOSED（正常）→ OPEN（跳闸 30 秒）→ HALF_OPEN（放 1 个探针）→ 成功恢复 / 失败重新跳。
3. 熔断管"持续故障"，重试管"偶发抖动"，降级管"换个下游继续给用户答案"，三者各管一件事。
