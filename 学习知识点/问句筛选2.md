## B. 逐字符拆开这一行

```python
hits = [h for h in scored if h.score >= self._min_score][:k]
```

从前到后一共 5 个零件：

| 片段 | 名称 | 作用 |
|---|---|---|
| `for h in scored` | 迭代源 | 遍历**已排序**的候选列表，每个元素是一个 `ToolHit` |
| `h.score` | 取分 | `ToolHit` 是个具名元组式对象，`.score` 就是这一步算出来的相关度 |
| `>= self._min_score` | 保底条件 | 及格线（默认 **0.25**，来自 `TOOL_RAG_MIN_SCORE`）；`>=` 含等号 |
| `[ ... ]` 第一层 | **过滤**（filter） | 只保留及格的，**不补位**——砍掉几个就少几个 |
| `[:k]` 第二层 | **截断**（slice） | 从头取 k 个（默认 **5**，来自 `TOOL_RAG_TOP_K`） |

必须记住的一个事实：**`[:k]` 作用在过滤之后的列表上**，不是作用在 `scored` 上。

## C. 数据形态的逐步演变（实测）

构造 6 个工具、提问 `"查询天气"`，把每一步打印出来：

```
q_frags=['查询', '询天', '天气'] (共 3 段)          ← 中文 2-gram 切片
```

### 场景 1：`min_score=0.25, top_k=2`（只有过滤生效）

```
A 未排序 hits  : [(t1_天气查询服务,0.4), (t2_城市天气,0.2), (t3_天气,0.2), (t4_报销查询,0.2), (t6_查天气,0.2)]
B 排序后 scored: [(t1_天气查询服务,0.4), (t2_城市天气,0.2), (t3_天气,0.2), (t4_报销查询,0.2), (t6_查天气,0.2)]
C 过滤 >= 0.25 : [(t1_天气查询服务,0.4)]                    剩 1/5   ← 砍掉 4 个
D 截断 [:k] k=2: [(t1_天气查询服务,0.4)]                    ← 只剩 1 个，截断没东西可截
E recall 一致? True
```

分数怎么来的：`hit / len(q_frags) × 0.6`
- `t1` 命中 `查询`+`天气` = 2/3 = 0.6667 × 0.6 = **0.4**
- `t2/t3/t6` 各命中 1 段 = 1/3 = 0.3333 × 0.6 = **0.2**
- `t4_报销查询` 命中 `查询` = **0.2** ← 注意这个噪声：它跟"天气"毫无关系，只因为共享"查询"二字就进了候选，正是 `min_score` 要挡的东西
- `t5_计算器` 命中 0 段 → 在 `if not hit: continue` 那一步就被跳过了，**根本没进 scored**

### 场景 2：`min_score=0.15, top_k=2`（过滤 + 截断都生效）

```
C 过滤 >= 0.15 : [(t1,0.4), (t2,0.2), (t3,0.2), (t4,0.2), (t6,0.2)]   剩 5/5  ← 一个没砍
D 截断 [:k] k=2: [(t1,0.4), (t2,0.2)]                                   ← 截断砍掉 3 个
```

**对比两个场景就看清了两个动作的分工**：
- 阈值 = 管**质量**（不达标的不要，宁缺毋滥）
- `[:k]` = 管**数量**（合格的太多，只带前 k 个进 prompt）

### 场景 3：真实目录（12 个远程工具，关键词路径）

```
0 工具总数: 12
1 q_frags: ['我的','的报','报销','销单','单到','到哪','哪一','一步','步了']   ← 9 段
2 有重合的工具数: 1
   finance_reimbursement_query  命中=2/9  raw=0.2222  score=0.1333
3 scored(已排序): [('finance_reimbursement_query', 0.1333)]
4 过滤 min_score=0.25 后: []   (剩 0/1)          ← 唯一候选被砍
5 截断 [:k] k=5 后: []
6 recall 实际返回: []
```

**这就是"过滤"最有威力的地方**：宁可返回空，也不把 0.1333 的工具塞进 prompt。返回空之后由路由层兜底（见 H 节）。

## D. 过滤 vs 截断：为什么必须两个都要

| 只有 `[:k]`（不要阈值） | 只有阈值（不要 `[:k]`） |
|---|---|
| 库里没有相关工具时，**照样返回 k 个无关工具** | 热门词能把 20 个工具全部判定及格，全进 prompt |
| 场景 1 会返回 `[t2, t3]`（分数仅 0.2） | 场景 2 会返回 5 个，prompt 爆 token |
| 模型被迫在垃圾候选里挑 | 精确率崩盘 |

一句话：**`[:k]` 是「取前 k 个」，`min_score` 才让它变成「取好的 k 个」。** 这也是源码注释里写死的那句（`tool_rag.py:151-154`）。

## E. `sort` 是这一行的前提（实测反例）

上一行 `scored.sort(key=lambda h: h.score, reverse=True)` 不是可选的装饰。实测：

```python
raw = [ToolHit("t5_计算器",0.05), ToolHit("t2_城市天气",0.2), ToolHit("t1_天气查询服务",0.4)]   # 乱序

A 不排序 [:2]          : [(t5_计算器,0.05), (t2_城市天气,0.2)]     ← 拿到最差的，漏掉 0.4 的
B 排序后 [:2]          : [(t1_天气查询服务,0.4), (t2_城市天气,0.2)]
C 先过滤(>=0.25)后截断 : [(t1_天气查询服务,0.4)]                   ← 正确
D 先截断后过滤         : []                                        ← 空的！高分被截掉了
```

**这修正一个常见误解**：说"先过滤和先截断结果一样"——只有在**已排序**时才成立（场景 1/2 的 B→C→D 就是证据）。乱序时先截断会**永久丢失高分项**，因为 `[:k]` 根本没看到它。

另外 `sort` 的两个细节：
- `key=lambda h: h.score` —— 按分数排序，`ToolHit` 本体不动
- `reverse=True` —— 降序，高分在前（后面 `[:k]` 才是"取最好的 k 个"）
- Python 的 `sort` 是**稳定排序**：分数相同的 `t2/t3/t4/t6`（都是 0.2）保持原插入顺序，所以场景 2 截断取到的是 `t2` 而不是随机一个——**同分时结果是确定的，可复现**

## F. 边界矩阵（全部实测）

| 情况 | 结果 | 说明 |
|---|---|---|
| `score == min_score` | **保留** | `>=` 含等号。实测 `min_score=0.2` 时 `data_city_weather=0.2` 被留下（`7 min_score=0.2 命中: [('data_city_weather', 0.2)]`）；改成 `>` 它会静默消失 |
| `score` 略低于阈值 | 丢弃 | 实测 0.1333 < 0.25 → 空列表 |
| 候选数 < k | 返回全部及格项，**不补位** | 场景 1 返回 1 个而不是 2 个 |
| 候选数 > k | 取前 k 个 | 场景 2 由 5 个截到 2 个 |
| 全被过滤掉 | 返回 `[]` | 由路由层兜底 |
| `min_score=0` | 全收（实测 `9 min_score=0 命中数: 1`） | 等于关掉质量闸门 |
| 索引为空 | `[]` | `recall` 开头 `if not self._texts: return []`（165 行）根本走不到这行 |
| `top_k` 传 0 或负 | `k = max(1, ...)` 兜底成 1（167 行） | 不会出现"取 0 个" |

## G. 上游：`score` 到底是怎么算出来的

两条路径，都产出 `ToolHit(name, score, source)`：

**① 向量路径**（`tool_rag.py:189-192`）：`score = round(余弦相似度(qv, vec), 4)`
- `qv` = 提问的 1024 维向量（`embed(query)`）
- `vec` = 每个工具画像文本的向量（建索引时批量编码，109 行）
- 余弦相似度范围 `[-1, 1]`，语义越近越接近 1
- 实测线上档：`finance_reimbursement_query=0.5384`、`finance_invoice_submit=0.3988`、`it_ticket_create=0.3351`

**② 关键词路径**（`tool_rag.py:214-215`）：`score = round(min(1.0, 命中段数/提问段数) × 0.6, 4)`
- 乘 `0.6`（`_KEYWORD_SCALE`）是因为字面重合的证据强度弱于语义，不折算会盖过真实语义命中
- 上限被 `min(1.0, ...)` 钳住，最高 0.6

两条路径**最后都跑同一行**：`sort → 过滤 → 截断`。

## I. 三种等价写法

**① 普通循环版（最容易读）**

```python
scored.sort(key=lambda h: h.score, reverse=True)
hits = []
for h in scored:
    if h.score < self._min_score:      # 不及格：跳过（不补位）
        continue
    if len(hits) >= k:                 # 够了就停
        break
    hits.append(h)
```

**② 分步版（调试时最清楚）**

```python
scored.sort(key=lambda h: h.score, reverse=True)
passed = [h for h in scored if h.score >= self._min_score]   # 过滤
hits   = passed[:k]                                          # 截断
```

**③ 带诊断版（想看每一步发生了什么）**

```python
scored.sort(key=lambda h: h.score, reverse=True)
passed = [h for h in scored if h.score >= self._min_score]
dropped = len(scored) - len(passed)
hits = passed[:k]
trimmed = len(passed) - len(hits)
_logger.debug(
    f"召回: 候选={len(scored)} 阈值砍掉={dropped} 超量截断={trimmed} 最终={len(hits)}"
)
```

## J. 五个最容易搞错的点

1. **`>=` 不是 `>`**：等于阈值算及格，实测 0.2 对 0.2 被留下。
2. **返回的可以少于 k，也可以为空**：它不做补位，空了交给路由兜底。
3. **`sort` 是这一行的地基**：没有它，`[:k]` 取的是"碰巧在前面的 k 个"，实测会拿到 0.05 而漏掉 0.4。
4. **`h.score` 有两个来源**：向量路径是余弦值（可到 0.9+），关键词路径被乘了 0.6（上限 0.6）。**同一个 `min_score=0.25` 在两个路径下的严格程度不一样**——关键词路径更难达标（场景 3 里 0.1333 就被砍了，而向量路径同样的问题能给到 0.5384）。
5. **这不是最后一道截断**：后面 `router.py:216` 还有 `[:max_tools]`。

## K. 可调旋钮与总结

| 旋钮 | 默认 | 作用 |
|---|---|---|
| `TOOL_RAG_TOP_K` | 5 | 这里的 `k`，召回最多给几个 |
| `TOOL_RAG_MIN_SCORE` | 0.25 | 这里的 `self._min_score`，及格线 |
| `AGENT_MAX_TOOLS` | 8 | 路由层合并后的硬截断 |
| `TOOL_RAG_ENABLED` | true | 关掉后整段跳过，全量工具进池 |

**一句话**：这一行 = **排序后的候选里，先按 `min_score` 砍掉不合格的（不补位），再取前 `top_k` 个**；`[:k]` 管数量、阈值管质量，两者缺一不可，而 `sort` 是这一切成立的前提。
