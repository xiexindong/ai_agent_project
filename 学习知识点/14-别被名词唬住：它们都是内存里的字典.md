# 别被名词唬住：全量池和 Tool-RAG 都是内存里的字典

> 配套代码：`modules/agent/router.py`、`modules/tools/tool_rag.py`、`modules/tools/tool_registry.py`、`modules/mcp/gateway.py`
> 一句话结论：**它们的存储方式没有任何区别，都是内存 dict/list；区别只在"存的是什么"——一个存能执行的完整定义，一个存只够算相似度的最小画像。**

---

## 一、先把名词拆穿

项目里出现了好几个听起来很唬人的词：全量候选池、Tool-RAG 索引、工具注册表、网关目录。落到代码里，它们其实都是最普通的数据结构：

| 名词 | 本质 | 代码位置 |
|---|---|---|
| 全量候选池 `pool` | 一个 `dict` + 一个 `list` | `router.py:156-157` |
| Tool-RAG 索引 | 三个 `dict` | `tool_rag.py:67-69` |
| 工具注册表 | 一个 `dict` | `tool_registry.py` `_tools` |
| 网关目录 | 一个 `dict`（+ 一个落盘的 json） | `gateway.py` `_tool_index` |

```python
# router.py:156-157 —— 全量池
pool: Dict[str, object] = {}        # 工具名 -> 工具对象（本地）或目录条目（远程）
pool_names: List[str] = []          # 候选池名字列表，保序去重

# tool_rag.py:67-69 —— Tool-RAG
self._texts: Dict[str, str] = {}                  # 工具名 -> 用途画像文本
self._vectors: Dict[str, List[float]] = {}        # 工具名 -> 语义向量
self._metas: Dict[str, dict] = {}                 # 工具名 -> 原始元信息
```

**没有数据库、没有外部存储、没有 RPC**。整个工具体系里唯一落盘的东西是 `data/mcp_catalog.json`——一个存工具元数据的**文本文件**，而且存的不是向量。

> 前面用"权威源"这种说法容易让人误以为它是个存储系统。**它就是内存字典**。

---

## 二、那既然都是内存数组，为什么要分两个？

**区别不在"存在哪"，而在"存的是什么"。**

同一个工具 `weather`，在两处的形态完全不同：

```python
# 全量池：存的是【工具本体 / 完整定义】
pool["weather"] = {
    "name": "weather",
    "description": "查询城市天气",
    "inputSchema": {                          # 完整 schema
        "type": "object",
        "properties": {"city": {"type": "string"}},
        "required": ["city"],
    },
    "server": "enterprise-mcp",
}
#   ↑ 能拿去执行、能生成 Function Calling schema


# Tool-RAG：存的是【裁剪过的画像 + 向量】
_texts["weather"]   = "weather。查询城市天气 可填参数: city"    # 一句话文本
_vectors["weather"] = [0.012, -0.034, ...]                      # 1024 维向量
#   ↑ 只能算相似度，不能执行
```

|  | 全量池 | Tool-RAG |
|---|---|---|
| 内容 | 完整定义（含 schema 的类型 / 必填 / 结构） | 一句画像文本 + 向量 |
| 能不能执行 | 能（本地实例 / 可连的目录条目） | **不能**，只是字符串和数字 |
| 用途 | 取回本体、生成 schema、执行 | 算相似度、排序、挑名字 |
| 缺了什么 | 无 | 丢掉了参数类型、必填约束、枚举值 |

**关键点**：Tool-RAG 存的是**有损压缩后的副本**，专门为"算相似度"这一件事而存在。它替代不了全量池，因为从它那儿拿不到能用的 schema。

---

## 三、比喻：完整档案 vs 照片墙

- **全量池** = 员工的**完整档案**（身份证、技能证书、联系方式、报价单）
- **Tool-RAG** = 一张**照片墙 + 相似度打分表**（只有照片和"谁跟需求最像"的分数）

两者都是纸、都放在同一个办公室里（都是内存）。但**拿着照片你联系不上人**，得回档案柜取完整档案。

这就是为什么流程必须"召回名字 → 回查本体"，而不能直接用召回结果去调用。

---

## 四、画像文本是怎么被"压缩"的

看一眼这个压缩有多狠：

```python
# tool_rag.py:250-254
@staticmethod
def _routing_text(name: str, description: str, schema: dict) -> str:
    props = (schema or {}).get("properties", {}) or {}
    params = "、".join(list(props.keys())[:6]) or "无参数"
    return f"{name}。{description} 可填参数: {params}"
```

输入一个完整的 schema，输出是：

```
weather。查询城市天气 可填参数: city
```

被丢掉的信息：

- 参数 `city` 的**类型**（string？number？）
- 是否**必填**（required）
- 嵌套结构、枚举值、默认值
- **超过 6 个的参数直接不写**（`[:6]`）

**这些恰恰是调用工具时必须知道的**。所以画像文本天生只能用来"挑"，不能用来"调"。

> `tool_rag.py` 开头 14-18 行的设计说明写得很清楚：存用途画像，不存调用契约。把契约也塞进索引，等于把「怎么调」和「该不该调」混在一起，既浪费空间，又让召回混入参数噪声。

## 五、还有一个实际差异：生命周期不同步

|  | 生命周期 | 说明 |
|---|---|---|
| `pool` | **一次 `route()` 调用** | 函数结束就没了；每轮从 registry + gateway 重新灌一遍（159-175 行） |
| Tool-RAG | **整个进程** | 持续累积，只有 `clear()` 才清空 |

后果：**两者可能不一致**。工具已下线时，Tool-RAG 索引里还留着它的向量，而 `pool` 里已经没有了。

这正是 211 行那道校验存在的原因：

```python
# router.py:210-213
for hit in self.tool_index.recall(query, top_k=self.top_k):
    if hit.name in pool and hit.name not in scores:
        #              ↑ 召回的名字必须在刚建好的全量池里还活着
        rag_hits.append(hit.name)
        scores[hit.name] = hit.score
```

防止"索引里有、但目录里已经没了"的**僵尸工具**被派给模型。

## 六、一个延伸问题：能从 Tool-RAG 直接拿全部工具吗？

**能拿到全部名字**（`_texts.keys()`），但**拿不到能用的定义**。

因为 schema 在存进去之前就被裁掉了。想列举全部工具，正确的入口是：

```python
all_local   = registry.list_tools()      # 本地工具实例（完整）
all_remote  = gateway.catalog()          # 远程目录条目（完整）
all_names   = set(t.name for t in all_local) | set(e["name"] for e in all_remote)
```

Tool-RAG 只回答"哪个最像"，不回答"它长什么样"。

## 七、四个"听起来像数据库"的东西，真实身份一览

| 名词 | 真实身份 | 是否持久化 | 备注 |
|---|---|---|---|
| 全量候选池 `pool` | 函数内的局部 dict | 否 | 一次路由结束即销毁 |
| Tool-RAG 索引 | 实例上的三个 dict | 否 | 进程内常驻，`clear()` 才清 |
| 工具注册表 `ToolRegistry` | 实例上的一个 dict | 否 | 启动时构建，含本地实例 + 按需注册的远程适配器 |
| 网关目录 `_tool_index` | 实例上的一个 dict | **半持久化** | 本体在内存；元数据落盘到 `data/mcp_catalog.json` |

**唯一真正落盘的是 `data/mcp_catalog.json`**，而且它存的是工具元数据（名字/描述/参数的**文本**），不是向量。

所以整个工具体系的存储全景是：

```
内存（进程级）   ToolRegistry._tools        本地实例 + 已注册的远程适配器
内存（进程级）   gateway._tool_index        远程目录条目（含完整 schema）
内存（进程级）   tool_rag 三张表            画像文本 + 向量
内存（调用级）   router pool                每轮重建的全量合并视图
磁盘             data/mcp_catalog.json      远程工具元数据（文本，非向量）
```

**向量一次都没落过盘**——这是刻意的，上一份文档（12 号）讲过原因：向量绑定 embedding 模型和维度，容易作废；文本永远有效，重启后重新编码即可。

## 八、纠正一个容易误导的说法

我在 13 号文档里写「Tool-RAG 只是筛选器、不是数据来源」——这话结论对，但容易让人以为它是个外部系统。准确表述应该是：

> **Tool-RAG 是同一批工具的"第二份、有损的、只用于排序的内存副本"。**
> 它和全量池共享同一批工具，只是各存各的、各管一段。

两个结构**不是上下游关系**（不是"索引从池里生成数据"），而是**同一批工具的两种视图**：

```
        同一批工具（32 个）
        /              \
   完整视图            排序视图
   pool / registry     Tool-RAG
   （能执行）          （能排序）
        \              /
     召回名字 -> 回查完整视图 -> 执行
```

## 九、常见误解 Q&A

**Q：既然都是 dict，合并成一个不行吗？**
技术上能合并，但会互相拖累：完整 schema 塞进索引会让画像文本变长、引入参数噪声；而执行路径每次都要带着一堆用不到的向量。**按用途分开存，是职责分离，不是存储分层。**

**Q：Tool-RAG 的向量为什么不顺便存进 pool？**
因为 `pool` 每轮重建（159-175 行），而向量化要调 embedding（花钱、耗时）。放 pool 里等于**每轮对话重新编码一次全部工具**——这就是 181 行只做「增量索引」的原因：文本没变就不重算。

**Q：`_metas` 存的是什么，跟 `_texts` 重复吗？**
`_metas` 存原始元信息（来源 server、完整描述），供排查用；`_texts` 存压缩后的画像文本，供算相似度用。两者内容不同，前者完整、后者裁剪。

**Q：那磁盘上的 `mcp_catalog.json` 和内存里的 `_tool_index` 是什么关系？**
前者是后者的**持久化快照**。启动时：文件存在 → 读进来填 `_tool_index`（不连子进程）；不存在 → 连子进程拉目录 → 填 `_tool_index` → 写文件。

## 十、一句话总结

1. **全是内存结构**：pool 是 dict + list，Tool-RAG 是三个 dict，registry 是一个 dict——没有数据库参与。
2. **区别在内容不在介质**：pool 存能执行的完整定义，Tool-RAG 存只够算相似度的最小画像（丢掉了类型、必填、枚举）。
3. **Tool-RAG 是有损副本**，专用于排序，用完名字必须回查本体。
4. **生命周期不同步**：pool 一次调用即销毁，Tool-RAG 进程级常驻——所以有 `hit.name in pool` 这道防僵尸校验。
5. **向量从不落盘**，落盘的只有 `data/mcp_catalog.json` 这份元数据文本。
6. 两者是**同一批工具的两种视图**，不是上下游关系。
