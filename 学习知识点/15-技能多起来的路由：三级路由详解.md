# 技能那么多，是怎么挑出来的？（三级路由）

> 配套代码：`modules/skills/skill_registry.py`、`modules/skills/base_skill.py`、`modules/skills/builtin_skills.py`
> 一句话结论：**技能不用 Tool-RAG，走的是三级路由——L1 关键词（免费）→ L2 向量（模糊时）→ L3 LLM（兜底）。串行执行、命中即停，一次只走一条路。**

---

## 一、先说结论

| 问题 | 答案 |
|---|---|
| 技能多了怎么挑？ | 三级路由，逐级加码，不是全量向量召回 |
| 三级是并行投票吗？ | **不是，串行漏斗，命中即停** |
| 关键词和向量会同时用吗？ | 不会。L1 定不了才轮到 L2 |
| 向量能推翻关键词的结论吗？ | **不能**，L2 的候选池就是 L1 的输出 |
| 为什么工具能用 Tool-RAG，技能不行？ | 工具多选无害（top-k）；技能只能单选（SOP 混注会冲突） |
| 技能向量进 Milvus 吗？ | 不进。跟工具一样自己算余弦，存内存 `_vec_cache` |

---

## 二、为什么技能不能照抄 Tool-RAG

|  | 工具（Tool-RAG） | 技能（SkillRegistry） |
|---|---|---|
| 选几个 | **多个**（top-k，默认 5） | **最多一个**（或没有） |
| 误判代价 | 低：多给几个工具，模型自己挑对的 | **高**：激活错误 SOP 会带偏整轮对话 |
| 信号来源 | 自动生成的一句话画像 | **人工写的触发词** + 精心拼的 `routing_text` |
| 注入方式 | JSON Schema 列表，多份并存无害 | **整段 SOP 指令**，两份混着会冲突 |
| 数量级 | 可成百上千（远程 MCP） | 人工定义，当前 4 个 |
| 匹配策略 | 单层向量 top-k | **三层串行兜底** |

**最根本的一条**：技能注入的是一整段 SOP 作业流程，两个技能的 SOP 同时注入会互相打架；工具只是"候选清单"，多给几个完全无害。

所以：**工具要排序取 top-k，技能必须单选**——这个差异决定了两者走向完全不同的设计。

---

## 三、三级路由全景

```
用户提问
   |
   +- L1 关键词路由（零成本，全量扫一遍）
   |     对每个技能算「命中触发词权重和」
   |     短语 0.6 / 双字词 0.4 / 单字 0.15，累加封顶 1.0
   |        +- score >= 0.6（高阈值）-> 命中，结束
   |        +- score <  0.1（低阈值）-> 判定无关，走通用对话
   |        +- 卡在中间（模糊地带）   -> 下沉 L2
   |
   +- L2 向量语义路由（1 次 embedding）
   |     只对 L1 候选的【前 N 个】算余弦
   |        +- sim >= 0.75 -> 命中，结束
   |        +- 否则        -> 下沉 L3
   |
   +- L3 LLM 兜底（1 次 LLM 调用）
         只把【前 N 个候选】的名称清单丢给模型分类
         强制 JSON 输出 + 校验名字真实存在（防幻觉）
         confidence >= 0.5 -> 命中，否则未命中
```

它是**漏斗**：L1 零成本先砍掉绝大多数，L2/L3 只在剩下的少数候选里精判。

## 四、主入口：命中即停，一次只走一条路

```python
# skill_registry.py:343-355
def match(self, query, query_emb=None):
    decision, candidates = self._route_keyword(query)      # L1 先跑
    if decision == "hit":
        return candidates[0]        # 命中就 return，L2/L3 根本不执行
    if decision == "miss":
        return None                 # 判定无关也直接结束

    m = self._route_vector(query, candidates, query_emb)   # 只有 L1 说"模糊"才到这
    if m:
        return m                    # L2 命中就 return，L3 不执行

    m = self._route_llm(query, candidates)                 # 只有 L2 也没定才到这
    if m:
        return m
    _logger.info("技能未命中（L1/L2/L3 三层均未判定命中），走通用助手流程")
    return None
```

**不是"关键词 + 向量双路并行投票"**，而是串行短路：前一层能定就定，定不了才往下交。

## 五、L1 关键词路由：三档裁决

```python
# skill_registry.py:155-186
def _route_keyword(self, query):
    candidates = self.score_candidates(query)
    if not candidates:
        return "miss", []
    best = candidates[0]
    if best.score >= self._high:      # 默认 0.6
        return "hit", candidates
    if best.score < self._low:        # 默认 0.1
        return "miss", candidates
    return "ambiguous", candidates    # 卡在中间，下沉 L2
```

打分规则（`base_skill.py:75-91`）：

```python
_WEIGHT_PHRASE = 0.6    # 短语（3 字及以上）
_WEIGHT_WORD   = 0.4    # 双字词
_WEIGHT_CHAR   = 0.15   # 单字

hit_weight = sum(self._keyword_weight(kw) for kw in hits)
score = round(min(1.0, hit_weight), 4)
```

**按关键词长度分档给权重**——"报销流程"这种短语比"报"这种单字可信得多。得分是**累加**（不除以词表总权重），避免词表越大越难激活。

| L1 结论 | 条件 | 后续 |
|---|---|---|
| `hit` | ≥ 0.6 | 直接返回，结束路由 |
| `miss` | < 0.1 | 直接返回 None，走通用对话 |
| `ambiguous` | 0.1 ~ 0.6 | 下沉 L2 |

**「问句里出现了关键词」≠「会走向量」**：

- 命中一堆强触发词 → 证据充分，不再花 embedding 的钱
- 一个都没蹭上 → 判定无关，也不浪费
- 只蹭中一两个弱词（单字权重仅 0.15）→ 拿不准 → 才让向量帮忙

## 六、L2 向量路由：只在 L1 候选里重新排序

```python
# skill_registry.py:213-232
cands = candidates[: self._vec_top_n]        # ← 只取 L1 候选的前 N 个
qv = query_emb if query_emb is not None else get_embedding_service().embed(query)
vecs = self._skill_vectors([m.skill.name for m in cands])
scored = [(_cosine(qv, vecs[m.skill.name]), m) for m in cands if m.skill.name in vecs]
scored.sort(key=lambda x: x[0], reverse=True)
sim, best = scored[0]
if sim >= self._vec_threshold:               # 默认 0.75
    return SkillMatch(skill=best.skill, score=sim, route="vector", ...)
return None                                  # 不够高，下沉 L3
```

### 关键：L2 不能推翻 L1

**L2 的候选池就是 L1 的输出**（`candidates` 直接传进来）。L1 没提名的技能，L2 根本看不到。

向量只是在 L1 筛剩的几个里面**重新排序**，不是重新全量召回。L3 同理（`candidates[: self._llm_top_n]`，268 行）。

### 向量是懒加载 + 缓存的

```python
# skill_registry.py:188-199
def _skill_vectors(self, names):
    missing = [n for n in names if n not in self._vec_cache]    # 只编没编过的
    if missing:
        vectors = svc.embed_batch(texts)
        for name, vec in zip(missing, vectors):
            self._vec_cache[name] = vec
```

对比工具那边：

|  | Tool-RAG | 技能向量 |
|---|---|---|
| 存储 | `_vectors` dict | `_vec_cache` dict |
| 何时编码 | 启动时全量 `index_tools()` | **用到时才编**（懒加载） |
| 覆盖范围 | 全部工具 | 只编进过 L2 的候选 |

技能数量少且大部分问题 L1 就解决了，懒加载更划算——**可能整个进程跑完一个技能向量都没编过**。

### 余弦也是自己算

```python
# skill_registry.py:42-67
```

比 Tool-RAG 多一层：优先 numpy，降级纯 Python。同样**不进 Milvus**。

## 七、为什么必须有 L3（工具那边不需要）

代码注释里写得直白（`skill_registry.py:210-211`）：

> 坑：向量分不出「查账号」和「注销账号」这种动作相反的说法，所以它只负责选出候选，最终仍由阈值把关，宁可漏判也不误判。

**余弦相似度只看语义相近，不看动作方向**。「注销账号」和「注册账号」的向量非常接近，但要求执行的操作完全相反。

- **工具场景无所谓**：多召回一个工具，模型自己判断
- **技能场景致命**：激活错 SOP = 整轮跑偏

所以技能必须留一层**真正理解语义的 LLM** 兜底。L3 的两条硬约束（262-264 行）：

1. **强制结构化 JSON 输出**，不让模型自由发挥长文本
2. **必须校验返回的 skill_name 真实存在**，防幻觉；置信度不够按未命中处理

```python
# skill_registry.py:308-321
if not name or name.lower() in ("none", "null", "无"):
    return None                      # 模型主动说没有
skill = self._skills.get(name)
if skill is None:
    return None                      # 幻觉：返回了不存在的技能名
if confidence < self._llm_confidence:
    return None                      # 置信度不够
```

## 八、技能画像比工具画像丰富得多

工具画像（Tool-RAG，`tool_rag.py:250-254`）：

```
weather。查询城市天气 可填参数: city          <- 就一句话
```

技能画像（`base_skill.py:102-117`）：

```
数学计算。处理数学表达式求值 典型问法: 计算、算一下、等于多少、求和。1. 识别表达式
^展示名   ^描述              ^人工写的触发词              ^SOP 首句
```

`routing_text` 把**展示名 + 描述 + 触发词 + SOP 首句**拼成一段话。注释里说明了原因：单独用 `description` 太短，向量区分度不够。

|  | 工具画像 | 技能画像 |
|---|---|---|
| 生成方式 | 自动拼（名字 + 描述 + 前 6 个参数名） | 人工写触发词 + 多段拼接 |
| 长度 | 一句话 | 一段话 |
| 判别力 | 弱（这是工具召回的瓶颈） | 强 |

## 九、技能与工具在路由器里怎么配合

```python
# router.py:200-216
chosen = []
if skill is not None:
    for name in getattr(skill, "bound_tools", []) or []:
        chosen.append(name)
        scores[name] = 1.0          # 技能绑定的工具：强绑定，不参与排序

if self.tool_index:
    for hit in self.tool_index.recall(query, top_k=self.top_k):
        if hit.name in pool and hit.name not in scores:
            rag_hits.append(hit.name)

merged = chosen + rag_hits          # 技能绑定的排前面，语义召回的补后面
```

**技能主导，Tool-RAG 补充**：

- 命中技能 → 它绑定的工具**无条件进名单**（分数 1.0）
- 没命中技能 → 才靠语义召回凑

这就是为什么日志里的 reason 会区分：

| 情况 | reason |
|---|---|
| 都有 | 技能绑定 N 个 + 语义召回 M 个 |
| 只有技能 | 技能绑定 N 个（语义召回无达标结果） |
| 只有召回 | 无技能命中，按语义召回 M 个 |
| 都没有 | 技能未命中且语义召回为空，回退默认工具兜底 |

## 十、两种「多路」的对比（容易混淆）

|  | 技能路由 | 工具召回 |
|---|---|---|
| 层级关系 | **串行漏斗，命中即停** | 多个来源**并行合并** |
| 多路并存？ | 否，一次只有一条路生效 | **是**，`merged = chosen + rag_hits` |
| 结果数量 | 0 或 1 个技能 | 多个工具（top-k） |

**工具那边的"两条路"是真的并存**（技能强绑定 + 语义召回拼在一起）；**技能这边是三路择一**。

## 十一、一个值得注意的后果

因为 L2/L3 只在 L1 的候选里挑，**L1 判定 miss 时它们根本不执行**：

```
L1: score = 0 -> decision = "miss" -> 直接 return None
```

也就是说：**一个完全没命中任何触发词的新问法，不会被向量救回来。**

这是有意的（避免把明显无关的问题硬塞进某个技能），但也是可调的：

| 想改成什么样 | 怎么改 | 代价 |
|---|---|---|
| 让新说法也能命中 | 降低 `skill_low_threshold`，或 miss 时也下沉 L2 | 多花一次 embedding |
| 更严格，少误判 | 提高 `skill_high_threshold` | 更多问句下沉到 L2/L3，成本上升 |

## 十二、常见误解 Q&A

**Q：三条路会不会各给出一个技能，然后投票？**
不会。`match()` 是串行短路，第一个给出结论的层就 return，后面的层根本不执行。

**Q：L2 觉得另一个技能更像，能改判吗？**
只能在 **L1 提名的候选里**改判。L1 没提名的技能，L2 看不到。

**Q：为什么不让向量直接全量召回，多简单？**
两点：① 成本——全量编码所有技能 + 每次查询都比一遍，而 L1 是免费的；② 可控性——人工写的触发词比向量可靠，让向量推翻人工规则是本末倒置。

**Q：L3 一定会被调用吗？**
很少。只有 L1 模糊 **且** L2 相似度 < 0.75 时才触发。大部分问句在 L1 就结束了。

**Q：技能向量和工具向量能共用一个索引吗？**
现在是两个独立的 dict（`_vec_cache` / `_vectors`）。共用在技术上可行，但两者画像文本格式、阈值、候选范围都不同，合起来反而复杂。

## 十三、一句话总结

1. **技能不用 Tool-RAG**，走三级路由：L1 关键词（免费）→ L2 向量（模糊时）→ L3 LLM（兜底）。
2. **串行命中即停**，一次只走一条路，不是并行投票。
3. **L1 三档裁决**决定是否继续：≥0.6 命中、<0.1 放弃、中间下沉。
4. **L2/L3 不能推翻 L1**，候选池就是 L1 的输出。
5. **L3 不能省**：余弦分不出「查账号 / 注销账号」这类相反动作，技能误判代价太高。
6. **技能必须单选**（SOP 混注会冲突），工具可以 top-k——这个差异是两套设计的分水岭。
7. **技能向量同样自己算**（numpy 优先，降级纯 Python）、存内存 `_vec_cache`、**懒加载**，不进 Milvus。
8. **L1 判 miss 时 L2/L3 不执行**——完全没蹭中触发词的新问法不会被救回，这是有意取舍，可通过调阈值改变。
