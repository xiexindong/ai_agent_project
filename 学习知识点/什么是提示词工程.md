## 一、先看架子：`modules/prompt/` 四个文件

```
modules/prompt/
├── templates.py    一条提示词"长什么样"（模板 + 版本 + 变量表 + 渲染校验）
├── builtin.py      项目里那 8 条提示词"放在哪"（集中注册，带版本号）
├── strategies.py   这轮"怎么问"（zero_shot / few_shot / cot / react）
├── builder.py      "最终怎么拼"（四层拼装 + token 预算裁剪 + JSON 解析）
└── __init__.py     对外只暴露 11 个名字，内部结构不外露
```

**光是"把提示词从 agent 类里挪到一个专门的包"这件事，就已经是工程化的第一步**——它让"提示词"变成了一个**有归属的资产**，而不是附庸在某段逻辑里的字符串。

这一张表就是"配方本"。三条工程化的痕迹：

| 痕迹 | 体现 |
|---|---|
| **命名规范** | `模块.用途`（`react.system`、`summary`），不是 `PROMPT_1`。看到名字就知道是谁的、干什么的 |
| **同名多版本** | `react.system` 有 **v1 和 v2 两个版本并存**，这就是 A/B 对比和回滚的物质基础 |
| **带描述** | 第五个参数是给人看的一句话说明，`list_all()` 列出来就是一份交接文档 |

v2 是怎么来的？看它的来源注释：

```42:50:modules/prompt/builtin.py
# v2：在 v1 基础上追加两条约束，用于演示「改提示词 = 改一个版本」
#   追加内容对应两个真实问题：
#     1. 模型把工具结果复述一遍却不给结论（加"必须给出明确结论"）
#     2. 知识库为空时模型仍自行发挥（加"必须声明依据不足"）
_REACT_SYSTEM_V2 = _REACT_SYSTEM_V1 + (
    "\n\n## 补充约束\n"
    "- 工具已返回数据时，必须给出明确结论，不能只复述观察结果\n"
    "- 依据不足时，先说'当前资料不足以确定'，再说明还缺什么"
)
```

**这就是工程思维和手艺思维的分界**：改提示词不是"把原来那句覆盖掉"，而是**加一个新版本，保留旧版本，并且写清楚这次改动是针对哪个实测到的问题**。三个月后你还能回答"v2 当初为什么要加这两句"。

## 三、第 2 步：一条提示词被拆成四层

```6:14:modules/prompt/builder.py
【四层结构，为什么分四层】
    角色层     role          这轮对话模型"是谁"（企业助手 / 财务专员 / 审核员）
    策略层     strategy      这轮"怎么问"（zero_shot / few_shot / cot / react）
    上下文层   **context     这轮"拿什么答"（知识库、记忆、权限、工具清单）
    输出层     output_format 这轮"答成什么样"（纯文本 / JSON / Markdown）

    四层互不耦合：换策略不用动模板，换模板不用动裁剪逻辑。
```

对照 `react_agent.py` 里"改造前"的样子（注释里自己写了）：**模板、策略、上下文全写在一个 `format()` 里**，想单独调"怎么问"这一层，只能在那大段字符串里改。

拆层之后，`react.role` 模板里就**没有** "1. Reason / 2. Action / 3. Observation" 那一段了——那段归策略层：

```53:61:modules/prompt/builtin.py
#   【为什么要拆出一个 role 版】
```

## 四、第 3 步：变量由模板自己算出来，渲染前强制校验

模板里的变量**不是靠人维护一份清单**，而是代码扫出来的：

```83:90:modules/prompt/templates.py
@property
def variables(self) -> Set[str]:
    fields: Set[str] = set()
    for _, field_name, _, _ in string.Formatter().parse(self.template):
        if not field_name:
            continue
        fields.add(field_name.split(".")[0].split("[")[0])
    return fields
```

`react.reason` 那 8 个槽位（`query` / `skill_context` / `permission_context` / `rag_context` / `memory_context` / `tool_history` / `observation` / `tools_desc`）就是这么自动得到的。

然后渲染时强制比对：

```110:122:modules/prompt/templates.py
def render(self, **kwargs) -> str:
    need = self.variables
    missing = sorted(need - set(kwargs))
    if missing:
        raise PromptError(
            f"模板 {self.name}({self.version}) 缺少变量",
            f"missing={missing} provided={sorted(kwargs)}",
        )
    extra = sorted(set(kwargs) - need)
    if extra:
        _logger.warning(f"模板 {self.name} 收到多余变量 {extra}，已忽略")
        kwargs = {k: v for k, v in kwargs.items() if k in need}
    return self.template.format(**kwargs)
```

注意它**两个方向的策略不一样**：
- **缺变量 → 抛错**（因为会静默降质）
- **多变量 → 只告警**（因为调用方常常一次传整包上下文，多传是常态）

这不是随便定的，是权衡过的，注释里写明了理由（95-100 行）。

## 九、还有个"回归比对"的活儿

`examples/prompt_engineering_demo.py` 七幕，本质是**给提示词建的测试套件**：

```
第一幕 集中注册     第六幕 等价性：新渲染结果与现有 ReActAgent 的提示词逐字比对
第二幕 策略切换     第七幕 真实 LLM 调用（配了 key 才跑）
第三幕 变量校验
第四幕 预算裁剪     实测：rag_context 2040 token，预算 2000 → 截断到 1987，memory 丢弃
第五幕 少样本检索
```

第六幕尤其关键——它回答的是"**我这一通重构，有没有悄悄改掉模型的行为**"。工程化重构的铁律是：**先把"行为不变"证明出来，再谈优化**。

## 十、反例：还没工程化的部分（正好做对照）

同一项目里，这些提示词**仍然是散落的字符串**：


它们享受不到上面任何一条：没版本、没变量校验、没预算管理、改一句要翻文件、改完没法证明行为没变。

**这个"一半工程化、一半散落"的状态，就是理解"工程"二字最好的样本**——同一批人、同一个项目，一边有配方本一边只有便签纸，差别一目了然。

## 一句话总结

你这个项目里，"提示词工程"的"工程"具体落在 **6 个设施**上：

1. **集中注册表**（`builtin.py`）— 不再散落
2. **版本号**（v1/v2 并存）— 可回滚、可 A/B
3. **自动变量表 + 强制校验**（`templates.py`）— 缺了就炸，不静默降质
4. **策略独立成层**（`strategies.py`）— 换问法一个参数
5. **预算与优先级裁剪**（`builder.py`）— 资源有限时按代价排序
6. **回归比对**（`examples/..._demo.py` 第六幕）— 改完能证明行为没变

这六件里**没有一件是"把提示词写得更巧妙"**，全都管的是"怎么让一堆提示词在半年后还管得住"。这就是"工程"。
