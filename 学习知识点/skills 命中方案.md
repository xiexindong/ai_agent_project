# 实际开发选型：关键词 / 向量 / LLM路由
核心结论先说：**绝大多数生产级Agent，不是三选一，而是多级组合路由。**
先快速过选型判断，再讲落地架构、边界、坑。

## 一、三种方案适用场景对比
|方案|核心原理|适合场景|优点|缺点|
|---|---|---|---|---|
|**关键词/正则路由（你现在代码）**|字面关键词、正则，本地计算分数|指令固定、词汇变化小的任务（写github申诉、查订单、查天气）|零LLM调用、极低延迟、结果可复现、成本0|不认同义词；句式一变就匹配失败；需要人工维护关键词|
|**Embedding向量路由**|技能描述预编码embedding，用户query编码后算相似度|任务多、表达多样，但是不需要极强逻辑推理|能识别同义转述；比LLM路由便宜；速度中等|**无法区分细微歧义**；容易出现语义相近但意图不同的误匹配；embedding模型本身有成本|
|**LLM路由（把query+技能列表丢给大模型）**|LLM做意图分类，输出选中技能|意图复杂、歧义多、长自然语言、需要理解复杂约束|理解能力最强，同义、转述、模糊问句都能识别|token开销、延迟更高；会幻觉乱选；结果不稳定，需要输出校验|

> 一句话选型口诀：
> 简单指令优先**关键词**；
> 大量技能、自然语言表达多样 → **向量**；
> 歧义高、逻辑复杂，前两者都识别不准 → **LLM路由**。

## 二、工程最常用：多级路由架构（推荐你项目直接用）
```
用户问句 → 文本清洗 clean_query
    ↓
【第一层：关键词路由（你现在这套代码）】
    计算score
    if score > HIGH_THRESHOLD（例如0.6）：直接命中技能，结束路由 ✅
    elif score < LOW_THRESHOLD（例如0.1）：完全无命中，直接进入通用对话
    else：分数卡在中间，进入第二层
    ↓
【第二层：向量语义路由（可选）】
    向量检索TopN技能，拿相似度分数
    if 相似度 > vec_threshold：匹配技能，结束
    else：进入第三层
    ↓
【第三层：LLM路由兜底】
    把query + 候选技能清单丢给LLM，让模型选技能
    LLM输出技能名称，做校验，命中技能 / 无匹配，走通用对话
```
### 为什么这么分层？
1. 大部分高频简单query，**关键词直接搞定，不消耗任何LLM/Embedding**，省钱快响应；
2. 关键词识别模糊的query，交给向量做语义识别；
3. 真正歧义、复杂的query，才调用大模型兜底。

> 很多开源Agent框架（比如LlamaIndex、Langgraph、Dify）底层都是这套多级思路。

## 三、什么时候不推荐这么做，直接单选
### 场景A：内部小工具、技能很少（<10个技能），指令固定
👉 **只用关键词+正则**，不用向量、不用LLM路由。
例子：你的场景：github申诉、代码解释、查询文档等少数几个固定指令。
维护成本最低，足够用。
> 缺点：用户换说法就识别失败，需要持续补充关键词。

### 场景B：技能几十上百个，用户自然语言表达五花八门，预算有限
👉 **关键词 + 向量两级**，不启用LLM路由。
适合企业知识库、大量工具。
> 风险：语义相近意图不同的误召回（比如“查账号”和“注销账号”向量分数很高，但完全不同）。

### 场景C：开放对话、用户提问非常自由，歧义多，技能复杂
👉 **三级完整路由（关键词→向量→LLM）**
> 成本最高，但是意图识别能力最强。

## 四、落地开发注意的坑（非常关键）
### 1. 关键词路由
- 不要单纯 `kw in text`，要处理大小写、全角半角；
- 关键词容易冲突：`git` 同时出现在github技能、git代码技能，需要做**权重/互斥规则**；
- 关键词库需要持续迭代：收集用户未命中的query，定期新增关键词。

### 2. 向量路由
- 向量**不能做细粒度逻辑判断**，只能做语义相似度！
> 比如：“帮我删除仓库” 和 “帮我查看仓库”，向量相似度很高，但是动作完全不同，向量分不出来。
- 检索后一定要做**候选集过滤**，不要直接拿top1就判定命中。

### 3. LLM路由
- 不要让LLM自由输出长文本！强制结构化输出：JSON。
```
输出格式：{"skill_name": "xxx", "confidence":0~1}
```
- 必须做校验：判断返回的skill_name是否在注册的技能列表内，防止幻觉输出不存在技能；
- 不要每次都丢**全部技能清单**给LLM！
> 技能很多时，把前面关键词/向量筛选出的TopN候选技能传给LLM，减少token消耗。
> ✅ 优化：只传给LLM 2~5个候选技能，而不是全部几十上百个技能。

## 五、给你项目的建议（你当前项目现状）
你现在：少量技能，包含github申诉、代码相关，后端是Python+向量库。
✅ **推荐架构：关键词第一层 + LLM兜底（可以暂时不加上向量层）**
1. 先用你现有的关键词匹配代码；
2. 设置阈值：
   - score >=0.6：直接触发技能
   - 0 < score <0.6：进入LLM路由，只把候选技能列表丢给大模型判断
   - score=0：不触发技能，交给LLM普通对话
3. 技能数量少，向量层可以先不做，减少复杂度。

伪代码改造你的`build_skill_context`：
```python
def build_skill_context(self, clean_query):
    # 第一层：关键词匹配
    candidates = []
    for skill in self.skills:
        hits = [kw for kw in skill.trigger_keywords if kw.lower() in clean_query.lower()]
        score = len(hits)/len(skill.trigger_keywords)
        if score>0:
            candidates.append( (skill, score, hits) )
    # 按分数排序
    candidates.sort(key=lambda x:x[1], reverse=True)
    if not candidates:
        return None, SkillContext(score=0, params={})
    
    best_skill, best_score, hits = candidates[0]
    # 高阈值直接命中
    if best_score >=0.6:
        return SkillMatch(skill=best_skill, score=best_score, hit_keywords=hits)
    # 分数中等，进入LLM路由兜底，只传入候选技能
    else:
        llm_result = self.llm_route(clean_query, candidates)
        return llm_result
```

## 六、补充一个重要认知
> 路由（技能匹配）≠ 大模型执行技能。
路由：判断**要不要调用哪个工具**；
工具执行：拿到选中的技能，提取参数，执行函数，返回结果，再丢回大模型。
