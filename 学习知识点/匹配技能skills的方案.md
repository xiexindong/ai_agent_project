# ✅ 两个方案都存在！你现在看到的是【传统硬规则匹配】，你想象的那个【交给大模型做技能选择】是LLM路由（LLM Router），两种路线都在Agent项目里大量使用。

## 1）你现在手里这套：关键词/正则匹配（你现在代码这套）
```
用户问句 → 清洗文本 → 循环遍历所有技能trigger_keywords → 统计命中关键词 → 算出score → 判断是否触发技能
```
✅ 优点：
- 速度极快，**不调用大模型，没有token开销**
- 结果稳定可控，不会出现大模型幻觉乱选技能
- 适合固定关键词场景（比如github申诉、查天气这类明确指令）
❌ 缺点：
- 同义词识别差：关键词写`申诉`，用户写“找回账号”就匹配不到
- 句式灵活的自然语言容易漏匹配

> 这就是你当前代码 `hits = [kw for kw in self.trigger_keywords if kw.lower() in text]` 这一整套的逻辑。

## 2）你想象的方案：把问句+技能清单丢给大模型，让模型选技能（LLM路由）
伪代码示例：
```python
prompt = f"""
用户问题：{user_query}
可选技能列表：
1. github账号申诉：帮用户写GitHub2FA找回申诉材料
2. 计算器：数学计算
3. 翻译：文本翻译

请输出：应该调用哪个技能，只返回技能名称。
"""
resp = llm.chat(prompt)
matched_skill_name = resp.content
```
✅ 优点：理解语义，同义词、转述句都能识别
> 用户说：“我github账号2FA丢了，帮我写申诉” 和 “我的github两步验证没了，怎么找回账号” 都能识别同一个技能
❌ 缺点：
- 每次匹配都要调用大模型，消耗token、耗时
- 存在幻觉：偶尔乱选技能，稳定性不如关键词匹配
- 成本更高

## 3）还有第三种：向量语义匹配（介于两者中间，你之前项目向量检索可以用上）
把**每个技能的描述文本**预计算embedding存入向量库。
用户问句 → 生成embedding → 在向量库里检索最相似的技能，拿相似度分数做判断。
> 不调用LLM，只调用embedding模型；能理解语义，但比完整LLM路由便宜。

# 工程上常用组合方案（Agent后端主流）
**多级路由（优先快的，失败再上大模型）**
1. 第一步：先用你现在这套【关键词匹配】快速扫一遍
   - 如果命中分数高于高阈值 → 直接使用这个技能，结束（不走大模型，省token）
2. 如果关键词匹配分数很低，匹配不到
   - 进入第二步：**LLM路由**，把问句+技能列表丢给大模型做语义判断

> 这是很多Agent框架的标准做法：规则兜底 + LLM做复杂语义识别。

# 简单对比
|方案|是否调用大模型|能力|速度|
| ---- | ---- | ---- | ---- |
|关键词/正则匹配（你现在代码）|❌ 不调用|只能匹配字面关键词|极快|
|向量语义匹配|❌ 只调用Embedding|理解语义，同义词|较快|
|LLM路由（你想象的）|✅ 调用LLM|最强自然语言理解|慢，消耗token|
